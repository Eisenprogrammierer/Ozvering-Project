## `CHAT_STYLES_PLAN.md`

# План: игровой чат и стилевой слой общения

Статус: рабочий план. Разделы 3–4 сохранены как история первого
подхода (строковые `frames`/`prefix`/`suffix`/`closer`), признанного
недостаточным. Актуальная архитектура — регистровый профиль
реализатора, зафиксированная в разделе 11. Раздел 8 отражает
фактический прогресс.

## 1. Запрос пользователя

1. Добавить простой игровой чат: игрок выбирает автомат/фракцию и
   персонажа, с которым говорит, и пишет сообщения от лица своего
   игрового персонажа.
2. Проработать стилистическую составляющую общения: канцелярит
   (официальная переписка, доклад, приказ), дружеское, любовное общение
   и остальные регистры.

## 2. Жёсткие инварианты

- Диалог остаётся свободным русским текстом, без LLM, нейросетей,
  эмбеддингов и статистического ранжирования.
- Детерминизм: одинаковые мир, состояние диалога, стиль и ввод дают
  одинаковый ответ.
- Полная Data-Driven архитектура: стили, признаки, конструкции,
  обращения, маркеры и правила применения лежат в JSON. Python только
  интерпретирует данные.
- Стиль — только поверхностный слой. Он не выбирает факты, не меняет
  план ответа, не подменяет композиционный синтез и не превращается в
  выбор готовых ответов.
- Диалог read-only по отношению к кампании и BDI. Мост действий — только
  через намерения, как и раньше.
- Ровно 16 потребностей в `configs/characters/bdi.json` не трогать:
  нельзя добавлять, удалять или переименовывать.
- Шаблоны `realization.json` остаются только аварийным fallback.
- По фундаментальным архитектурным вопросам спрашивать пользователя, а
  не угадывать.

## 3. Архитектура стилевого слоя (первая версия, отвергнута)

### 3.1. Место в конвейере

Текущий путь ответа:

```
текст игрока
  → parser / fragment
  → состояние (QUD, референты)
  → AnswerPlanner (план + доказательство)
  → композиционный Realizer
  → Answer(kind, text, plan_id, proof, data)
  → память и сохранение
```

Первая версия встраивала стилевой слой последним шагом:

```
Answer → StyleEngine.apply(answer, style_id, knowledge) → Answer
```

### 3.2. Новые файлы и типы

- `configs/dialogue/styles.json` — единственный источник стилевых правил.
- `campaign/dialogue/style.py` — детерминированный интерпретатор.
- `campaign/dialogue/model.py`: `StyleSpec`, `StyleCatalog`, поле
  `DialogueCatalog.styles`.
- `campaign/dialogue/loader.py` — `load_styles()`, загрузка
  `default_style` у персон.
- `campaign/dialogue/lint.py` — проверка стилевых данных.
- `campaign/dialogue/engine.py` — хранение выбранного стиля,
  `set_style()`.

### 3.3. Схема styles.json (первая версия, отвергнута)

```json
{
  "schema": 1,
  "default": "neutral",
  "styles": {
    "official": {
      "id": "official",
      "label": "канцелярит",
      "register": "official",
      "address": {"m": "милостивый государь", ...},
      "frames": {
        "default": {"prefix": "Имею честь сообщить: "},
        "unknown": {"prefix": "К сожалению, ", "suffix": " ..."}
      },
      "closer": "С совершенным почтением, {speaker}.",
      "replacements": [{"find": "Да.", "replace": "Подтверждается."}]
    }
  }
}
```

Причина отказа: строковые `frames`/`prefix`/`suffix`/`closer` — это
декоративная обёртка готового предложения, а не стиль речи. Они дают
повторяющиеся неестественные формулы и по духу близки к FSM с
табличкой.

### 3.4. Набор стилей

1. `neutral` — ровный деловой регистр, без надстроек.
2. `official` — канцелярит, официальная переписка, формулы вежливости.
3. `report` — доклад: военная краткость, субординация.
4. `order` — приказ: властный регистр, прямота.
5. `friendly` — дружеское общение, близкая дистанция.
6. `romantic` — любовное общение, интимная дистанция.
7. `hostile` — враждебное общение, резкая прямота.
8. `mentor` — наставление, пояснение и вывод.

Список расширяемый: новый стиль добавляется только правкой JSON.

## 4. Метаданные игрока и говорящего

`AgentKnowledge` дополняется полями:

- `speaker_post`, `faction_name`;
- `player_id`, `player_name`, `player_post`, `player_faction`,
  `player_side`, `player_gender`.

Игрок ищется детерминированно: сначала персонаж с
`campaign_is_player=True` на `campaign.player_side`, затем обход
остальных фракций. Пол игрока берётся из
`campaign.data["player_identity"]["gender"]`, затем из атрибутов
персонажа; иначе нейтральное обращение.

`build_knowledge()` заполняет эти поля, не меняя кампанию и BDI.

## 5. Игровой чат

### 5.1. Новый экран

`view/screens/dialogue_chat.py`, класс `DialogueChatScreen(BaseScreen)`.

Экран:

- левая панель — список фракций-автоматов и персонажей выбранной
  фракции;
- правая панель — история сообщений, заголовок собеседника, выбор
  стиля ответа;
- нижняя строка — поле ввода и кнопка «Отправить»;
- кнопка «Назад» / ESC — возврат на экран автоматов.

Поведение:

- по умолчанию выбирается противник, если он есть, иначе первая
  доступная не-игровая фракция;
- персонаж по умолчанию — лидер, но игрок собственной фракции
  исключается из списка собеседников;
- мёртвые персонажи показываются, но не выбираются;
- сессии кэшируются по `(side, character_id)`, память общая через
  `app.dialogue_session()`;
- история сообщений хранится в экране и разделена по собеседникам;
- сообщения игрока подписываются именем его персонажа;
- ответы агента берутся из `session.respond(text).answer.text`, то есть
  уже проходят парсер, вывод, план и стиль.

### 5.2. Ввод текста

- `pygame.TEXTINPUT` для символов;
- `KEYDOWN` для Backspace, Enter, Escape;
- `pygame.key.start_text_input()` при открытии экрана,
  `stop_text_input()` при выходе;
- ограничение длины ввода, защита от падения без дисплея.

### 5.3. Выбор стиля

- стили берутся из `DialogueCatalog.styles`;
- чипы стилей в правой панели;
- выбранный стиль применяется к текущей сессии через
  `session.set_style(style_id)`;
- новые сессии получают текущий выбранный стиль;
- стиль по умолчанию — `persona.default_style` или
  `styles.default` (нейтральный).

### 5.4. Вход из экрана автоматов

В `view/screens/automata_screen.py`:

- кнопка «СВЯЗЬ» в свободной области сверху справа (`CHAT_RECT`);
- `_chat_rect()`, `_open_chat()`;
- обработка клика и отрисовка.

## 11. Актуальная архитектура: регистровый профиль реализатора

### 11.1. Диагноз

Строковые `frames`, `prefix`, `suffix` и `closer` — это не стиль речи,
а декоративная обёртка готового предложения. Она не выбирает факты, но
даёт повторяющиеся, неестественные формулы и по духу близка к FSM с
табличкой. Для требования «диалог должен идти естественно» этого
недостаточно.

### 11.2. Принцип

Стиль — это **регистровый профиль генерации**, а не постобработка
строки. Он участвует в выборе лексем, синтаксических конструкций,
порядка частей, обращений и дискурсивных связок. Содержание ответа
по-прежнему определяется планом и доказательством, а не стилем.

Слои, ставшие данными:

1. **Лексические регистры.** У одного смысла может быть несколько
   лексем: нейтральная, официальная, докладная, приказная, дружеская,
   любовная, враждебная, наставительная. Выбор — по регистру и
   синтаксическому контексту, с сохранением морфологии.
2. **Конструкции одного смысла.** Для отношения или речевого акта
   задаётся несколько конструкций, помеченных регистром, типом
   адресата и условиями. Это не готовые ответы, а грамматические
   деревья с слотами.
3. **Рекурсивные конструкции.** Главное предложение + придаточное,
   координация и подчинение. «Докладываю, что…» — конструкция с
   вложенной клаузой, а не строковый префикс.
4. **Обращения как именные группы.** Звательная/именительная форма,
   согласование по полу и числу, позиция в предложении. Обращение —
   часть синтаксиса, а не склейка строк.
5. **Дискурсивный планировщик.** Ответ может состоять из 1–3
   коммуникативных ходов: прямой ответ, обоснование, оговорка,
   заключение. Состав ходов определяется вопросом, знанием и видом
   ответа; стиль выбирает форму и связки, но не добавляет факты.
6. **Детерминированный антиповтор.** В `DialogueMemory` хранятся
   последние использованные конструкции. Политика из JSON запрещает
   повторять одну и ту же конструкцию N ходов подряд и выбирает
   следующий вариант по приоритету. Это не статистика: выбор объясним
   и воспроизводим.

### 11.3. Схема данных

```json
{
  "schema": 4,
  "default": "neutral",
  "styles": {
    "official": {
      "id": "official",
      "label": "канцелярит",
      "description": "Официальная переписка: высокий регистр...",
      "extends": "neutral",
      "register": "official",
      "features": {
        "formality": "high",
        "distance": "far",
        "directness": "indirect",
        "nominalization": "high",
        "address_mode": "post"
      },
      "selection": {"avoid_recent": 0}
    }
  }
}
```

Признаки стиля объявляются в `configs/dialogue/features.json`
(`dimensions` со значениями и умолчаниями). `extends` наследует
признаки и `selection` родителя; `register` — ключ профиля, он всегда
побеждает унаследованное значение.

### 11.4. Что меняется в коде

- `campaign/dialogue/style.py` — селектор регистра и профилей.
- `campaign/dialogue/features.py` — детерминированное сопоставление
  (число совпавших признаков, не вероятности; `avoid`/`recent`).
- `campaign/dialogue/realize.py`:
  - выбор лексемы по регистру (`_entry`, `_select`);
  - выбор конструкции по регистру и контексту (`_select`,
    `act_constructions`);
  - поддержка вложенных клауз (`_clause`, `conjunction`);
  - обращения как именные группы (`_address`, `address_mode` pre/post);
  - маркеры и частицы (`_marker`, `_particle`);
  - возврат трассы выбора (`_record`, `take_trace`:
    `construction_id`, `lexeme_id`, `address`, `marker`, `act`).
- `campaign/dialogue/answers.py` передаёт стиль в реализатор, а не
  оборачивает готовый текст; `Answer.data` получает `register`,
  `construction` (главная), `primary_construction`, `constructions`
  (полный список), `lexemes`, `construction_trace`.
- `campaign/dialogue/engine.py` хранит выбранный регистр и передаёт его
  в планировщик через `set_style`.
- `campaign/dialogue/coverage.py` — отчёт покрытия для
  ремонтопригодности.

### 11.5. Что НЕ меняется

- Парсер, грамматика входа, вывод, доказательства.
- Read-only отношение к кампании и BDI.
- 16 потребностей.
- Память, сохранения, QUD и референты.
- Запрет на LLM, эмбеддинги и статистическое ранжирование.
- Композиционный синтез как основа; `realization.json` остаётся
  аварийным fallback.
- Нейтральный стиль сохраняет прежний путь байт-в-байт
  (`StyleEngine.is_neutral` → `realize_act` возвращает `fallback`).

### 11.6. Решение по объёму переработки

Выбран **A. Полный регистровый реализатор**: лексические варианты,
несколько конструкций на смысл, вложенные клаузы, обращения,
дискурсивные маркеры и антиповтор. Вариант B (минимальный регистровый
слой без вложенных клауз и дискурсивного планировщика) отклонён.

## 0. Глубинная потребность

Игрок должен **разговаривать с разумными агентами мира на естественном
языке**, а не выбирать реплики из заранее написанного дерева вариантов.

При этом принципиальны пять ограничений:

1. **Полная Data-Driven архитектура.** Диалог, как и всё ядро, должен
   расширяться правкой JSON, а не Python. Онтология, лексикон, грамматика,
   правила вывода, политики ответа и конструкции синтеза — данные. Python
   знает только контракты и алгоритмы интерпретации. Любое расширение,
   требующее правки Python, — архитектурный разрыв, который фиксируется в
   [`DATA_DRIVEN_CORE_GAPS.md`](DATA_DRIVEN_CORE_GAPS.md), а не обходится
   молча.
2. **Без LLM и нейросетей.** Никаких языковых моделей, эмбеддингов,
   обученных ранжировщиков и внешних API.
3. **Белый ящик.** Любой ответ можно разложить на шаги: разбор фразы,
   логическая форма, факты, вывод, выбор речевого акта, синтез текста.
4. **Детерминизм.** При одном состоянии мира, одном состоянии диалога и
   одном вводе ответ совпадает побитово. Отладка воспроизводима.
5. **Полностью естественный язык.** Игрок не пишет запросы на DSL,
   не заполняет формы и не выбирает пункты меню. Он пишет или говорит
   обычной русской фразой.

NLG (генерация естественного языка) — не самоцель. Глубинная потребность
выше: **осмысленный ответ на произвольный вопрос в рамках мира**. Если
ответ можно собрать без «настоящей» грамматики, но он остаётся
естественным, связным и логически обоснованным, этого достаточно.
Однако шаблон «одна фраза на один вопрос» упирается в комбинаторику:
контекстов, целей и формулировок слишком много. Поэтому целевая
архитектура всё равно включает композиционный синтез, просто начинает
с упрощённого ядра.

### 0.1. Что именно запрещено и что разрешено

| Запрещено | Разрешено |
|---|---|
| LLM, трансформеры, embeddings | Словари, морфология, грамматики, унификация |
| Обучение на корпусе диалогов | Авторские правила и лексикон в JSON |
| «Чёрный ящик» с вероятностями | Детерминированный поиск с фиксированным порядком |
| Статистическое ранжирование ответов | Логический вывод и трассировка доказательства |
| Скрытые эвристики без объяснения | Явные правила приоритета, видимые в отладке |
| Показ игроку формального языка | Свободный ввод на русском |

Вероятности игровой модели (шанс работы, сила убеждения) — это **данные
мира**, а не статистика языка. Они могут входить в ответ как числа и
оценки, но не управляют разбором и выводом.

### 0.2. Data-Driven как первое требование

Диалоговый режим не является исключением из правила «контент — это
данные, код — это интерпретатор». Более того, именно диалог чаще всего
соблазняет спрятать содержание в Python: списки слов, ветки «если
спросили про X», захардкоженные ответы. Это запрещено.

| Слой диалога | Где живёт | Что делает Python |
|---|---|---|
| Онтология: типы, отношения, допустимые связи | `configs/dialogue/ontology.json` | Загружает и проверяет |
| Лексикон: леммы, формы, синонимы, роли | `configs/dialogue/lexicon.json` | Сопоставляет токены |
| Грамматика: конструкции, признаки, семантика | `configs/dialogue/grammar.json` | Унифицирует и строит разбор |
| Правила вывода: посылки, головы, объяснения | `configs/dialogue/rules.json` | Доказывает по правилам |
| Политики ответа: честность, табу, регистр | `configs/dialogue/personas.json` | Выбирает речевой акт |
| Конструкции синтеза: смысл → фраза | `configs/dialogue/synthesis.json` | Собирает поверхность |
| Темы и подсказки для уточнений | `configs/dialogue/topics.json` | Формулирует уточнение |
| Стили: регистровый профиль | `configs/dialogue/styles.json` | Согласует конструкции |
| Схема измерений стиля | `configs/dialogue/features.json` | Проверяет значения |

Критерий приёмки каждого этапа:

1. Новый тип сущности, правило, синоним, конструкция или стиль
   добавляются JSON-ом.
2. Линтер диалога проверяет ссылки, покрытие лексикона и неизвестные
   ключи.
3. Если для расширения всё-таки нужен Python, это оформляется как
   архитектурный разрыв с анализом и планом устранения.
4. Тест «JSON-only»: фикстура добавляет новый факт/правило/слово/стиль и
   получает работающий ответ без изменения `.py`.

## 1. Ключевое различие: диалог и «выбор из вариантов»

FSM-диалог выбирает следующую реплику из массива. Наш целевой диалог
**вычисляет содержание ответа**:

```
мир + BDI агента + история диалога + вопрос игрока
        │
        ▼
   разбор фразы  ──►  логическая форма
        │
        ▼
   проверка/вывод в базе знаний агента
        │
        ▼
   план ответа (что сказать, что скрыть, как объяснить)
        │
        ▼
   синтез русской фразы
        │
        ▼
   ответ + трассировка
```

FSM может остаться как **учёт фаз разговора** (приветствие, обмен
репликами, прощание), но не как источник содержания. Это важно: наличие
конечного состояния диалога не делает систему «FSM-диалогом», если ответ
порождается из фактов.

## 2. Мозговой штурм: пространство путей

Ниже — не один «правильный» путь, а карта вариантов с оценкой.

### 2.1. Путь A. Авторские шаблоны с подстановкой

**Идея.** На каждое намерение игрока — набор фраз с слотами
(`{agent}`, `{asset}`, `{value}`).

**Плюсы.** Дёшево, предсказуемо, легко проверять, не нужна морфология
(если формы заготовлены).

**Минусы.** Комбинаторика: вопрос «почему Империя считает Республику
незаконной, если её легитимность упала после эдикта?» требует отдельного
шаблона. Система быстро снова становится деревом вариантов. Годится как
**первый слой** и как fallback, но не как архитектура.

### 2.2. Путь B. Семантическая грамматика + унификация

**Идея.** Небольшая типизированная грамматика русского языка (chart
parser, Earley/CYK) с унификацией признаков. Правила сразу собирают
логическую форму (лямбда-исчисление / неодавидсоновские события).

**Плюсы.** Композиционность, разбор новых фраз, белый ящик, детерминизм,
естественная обработка падежей и порядка слов. Ошибки видны в дереве
разбора.

**Минусы.** Нужна морфология; авторская грамматика — это труд; возможна
неоднозначность и комбинаторный взрыв.

**Вывод.** Основной путь для понимания. Начинать с узкого, но
расширяемого ядра конструкций.

### 2.3. Путь C. Управляемый естественный язык (CNL)

**Идея.** Разрешить подмножество русского: вопросы, императивы, короткие
утверждения. Всё остальное — вежливая просьба уточнить.

**Плюсы.** Резко снижает сложность грамматики и лексикона, сохраняя
ощущение свободного ввода. Не DSL: игрок не учит формальный синтаксис,
просто система лучше понимает типичные конструкции.

**Минусы.** Если границы слишком узки, игрок чувствует ограничение.

**Вывод.** Разумная стратегия запуска: широкий лексикон, но умеренная
грамматика с постепенным расширением. Уточняющий вопрос — не провал,
а штатное поведение.

### 2.4. Путь D. Извлечение по ключевым словам / слотам

**Идея.** Ищем сущности и интенцию по словарю, не строя полный разбор.

**Плюсы.** Просто, быстро, устойчиво к опечаткам.

**Минусы.** Не различает «Империя атакует Республику» и «Республика
атакует Империю», плохо с отрицаниями, местоимениями и вложенными
вопросами. Как **fallback** после неудачного разбора — полезно.

### 2.5. Путь E. Формальный диалог с игроком на DSL

**Идея.** Игрок пишет `почему belief(empire, is_outlaw, republic)`.

**Плюсы.** Тривиально для реализации.

**Минусы.** Прямо нарушает требование «полностью на естественном языке».
**Отклонён.**

### 2.6. Путь F. Нейросетевой или статистический разбор

**Идея.** Обучить парсер/генератор на корпусе.

**Плюсы.** Высокая естественность.

**Минусы.** LLM/чёрный ящик, недетерминизм, невозможность трассировки.
**Отклонён по условию задачи.**

### 2.7. Путь G. Гибрид: грамматика + шаблоны + вывод

**Идея.** Грамматический разбор для входа, логический вывод для
содержания, композиционный синтез для выхода; шаблоны — только как
оптимизация и fallback.

**Плюсы.** Покрывает новизну, остаётся белым ящиком, позволяет поэтапное
внедрение.

**Минусы.** Самый большой объём работы; требует дисциплины слоёв.

**Вывод.** Целевая архитектура. Ниже она разложена по компонентам.

## 3. Целевая архитектура

### 3.1. Слои

```
┌──────────────────────────────────────────────────────────────┐
│ 1. Ввод: текст (позже — речь через внешний STT, не LLM)      │
├──────────────────────────────────────────────────────────────┤
│ 2. Нормализация: Unicode, регистр, ё/е, пунктуация, опечатки │
├──────────────────────────────────────────────────────────────┤
│ 3. Морфология: лемма, падеж, число, род, вид, время          │
├──────────────────────────────────────────────────────────────┤
│ 4. Синтаксис: chart parser по типизированной грамматике      │
├──────────────────────────────────────────────────────────────┤
│ 5. Семантика: логическая форма + discourse referents         │
├──────────────────────────────────────────────────────────────┤
│ 6. Диалог: состояние, QUD, общий фонд, обязательства         │
├──────────────────────────────────────────────────────────────┤
│ 7. Эпистемическая база: факты мира глазами агента             │
├──────────────────────────────────────────────────────────────┤
│ 8. Вывод: доказательство / контрмодель / отсутствие знания   │
├──────────────────────────────────────────────────────────────┤
│ 9. Планирование ответа: речевой акт, содержание, честность   │
├──────────────────────────────────────────────────────────────┤
│ 10. Синтез: глубинная структура → поверхность → морфология   │
├──────────────────────────────────────────────────────────────┤
│ 11. Трассировка: дерево разбора, логическая форма, вывод     │
└──────────────────────────────────────────────────────────────┘
```

### 3.2. Представление знаний

Нужны два вида знаний:

1. **Онтология мира** — типы и отношения: фракция, орган, персонаж,
   работа, актив, потребность, предикат убеждения, суть намерения,
   геометрический узел, событие.
2. **Правила вывода** — не статистика, а явные логические связи:
   «если фракция считает другую незаконной и требует её роспуска, то она
   в состоянии конфликта»; «если орган повреждён, его работа слабее».

Формат — типизированный Datalog/Prolog-подобный:

```json
{
  "id": "conflict_if_outlaw",
  "head": "conflict(?a, ?b)",
  "body": [
    "belief(?a, is_outlaw, ?b, ?v)",
    {"op": ">=", "left": "?v", "right": 0.5}
  ],
  "text": "{a} считает {b} вне закона, поэтому находится с ним в конфликте"
}
```

Движок: **обратный вывод с таблированием** (tabled resolution),
стратифицированное отрицание, фиксированный порядок правил. Никаких
вероятностных весов в самом выводе.

### 3.3. Эпистемическая модель

Агент отвечает **не по глобальному состоянию игры, а по своей модели
мира**. Это принципиально:

* персонаж может не знать факт;
* может знать устаревшую версию;
* может верить ложному;
* может намеренно скрывать или искажать.

Поэтому запрос идёт не к `AutomataCampaign` напрямую, а к адаптеру
`AgentKnowledge`, который собирает:

* BDI персонажа: убеждения с `value`, `confidence`, `source`, `ttl`;
* память о работах, событиях, разговорах;
* сведения фракции, доступные по должности;
* общий фонд диалога (что уже сказано игроку);
* геометрию и отношения, если они известны.

Глобальное состояние — источник для **проверки** и для отладки, но не для
прямого ответа. Это даёт честную ролевую асимметрию и объясняет, почему
два агента на один вопрос отвечают по-разному.

### 3.4. Логическая форма

Пример: «Почему Империя считает Республику незаконной?»

```
question(
  wh = why,
  body = belief(
    subject = faction:red,
    predicate = is_outlaw,
    object = faction:blue,
    value = ?v
  )
)
```

Пример: «Что ты собираешься делать с портом?»

```
question(
  wh = what,
  body = intention(
    subject = agent,
    object = node:port,
    essence = ?e
  )
)
```

Форма типизирована: `faction`, `organ`, `character`, `node`, `work`,
`asset`, `need`, `predicate`, `essence`. Неизвестное слово не превращается
в «мешок слов», а либо привязывается к типу через лексикон, либо вызывает
уточнение.

### 3.5. Речевые акты

Входные:

* вопрос да/нет, wh-вопрос, альтернативный вопрос;
* просьба, приказ, предложение, обещание, угроза;
* утверждение, жалоба, благодарность, оскорбление;
* приветствие, прощание, small talk.

Выходные:

* прямой ответ, частичный ответ, «не знаю»;
* уточнение, встречный вопрос;
* отказ, уклонение, ложь, умолчание;
* обещание, угроза, условие;
* объяснение с цепочкой причин;
* светская реплика.

Выбор акта — из данных о личности, должности, отношениях и текущей цели
агента. Это **не** языковая статистика, а приоритеты и правила.

### 3.6. Планирование ответа

Планировщик получает:

* логическую форму вопроса;
* результат вывода (доказательство, контрмодель, неизвестность);
* эпистемический статус (знает / верит / подозревает / не знает);
* политику раскрытия (`honest`, `evasive`, `boastful`, `paranoid`,
  `loyal`, `mercantile`);
* отношения с игроком;
* ограничения вежливости и субординации.

И возвращает **план содержания**:

```
answer_kernel:       "Республика — вне закона"
supporting_facts:    [эдикт, отказ подчиниться, решение суда]
withheld_facts:      [тайная поставка]
stance:              "уверенно"
hedges:              []
```

Только после этого начинается синтез. Это разделение критично: можно
тестировать «что агент решил сказать» отдельно от «как он это сказал».

### 3.7. Синтез текста

Три уровня, каждый детерминирован:

1. **Глубинная структура.** Пропозиции, роли, связи (причина, контраст,
   условие), тема-рема.
2. **Синтаксическая реализация.** Конструкции русского языка:
   подлежащее-сказуемое-дополнение, безличные, пассив, придаточные,
   вводные. Выбор конструкции — по правилам, не по вероятностям.
3. **Морфология и орфография.** Согласование, падежи, видовременные
   формы, предлоги.

Для MVP допустим **гибрид**: типизированные шаблоны конструкций
(не целых ответов) + слоты + морфологический синтез. Постепенно шаблоны
заменяются композиционными правилами.

Вариативность без недетерминизма: несколько конструкций на одно
значение, выбор по детерминированному ключу
`hash(agent_id, turn, proposition_id)`. Один и тот же контекст даёт один
и тот же текст, но разные агенты и ходы звучат по-разному.

### 3.8. Замкнутый цикл

```
игрок → разбор → обновление диалогового состояния
      → вывод в модели агента → план ответа → синтез
      → ответ игроку → (игрок снова) ...
```

Состояние диалога включает:

* `QUD` — стек обсуждаемых вопросов;
* `common_ground` — факты, принятые обеими сторонами;
* `commitments` — обещания, угрозы, сделанные предложения;
* `discourse_referents` — упомянутые сущности для местоимений;
* `last_answers` — чтобы не повторяться;
* `mood` — тон и терпение агента;
* `trace` — журнал шагов для отладки.

Цикл **не создаёт события мира** и не меняет кампанию, пока это не
разрешено отдельным слоем действий. На первом этапе диалог строго
read-only: он читает мир и BDI, но не применяет эффекты. Это сохраняет
контракт «события — ролевой слой, а не ядро» и не ломает детерминизм
кампании.

## 4. Морфология и лексикон

Русский язык требует морфологии. Варианты:

| Вариант | Плюсы | Минусы |
|---|---|---|
| Курируемый словарь форм в JSON | Полный контроль, JSON-only | Много ручной работы |
| Правила словоизменения + леммы | Компактно, расширяемо | Покрывает не всё |
| Внешний морфологический анализатор (словарный, не нейросетевой) | Широкое покрытие | Зависимость, риск «чёрного ящика» |

Рекомендация: **интерфейс `Morphology`** с двумя реализациями.

* `DictionaryMorphology` — курируемые леммы и таблицы форм, правило
  согласования. Обязательная база, работает без внешних зависимостей.
* `ExternalMorphology` — опциональный адаптер к словарному анализатору
  (например, pymorphy3), явно помеченный как не-нейросетевой. Включается
  флагом, не обязателен для игры.

Лексикон — данные:

```json
{
  "faction:red": {
    "lemma": "Империя",
    "type": "faction",
    "forms": {
      "nom": "Империя",
      "gen": "Империи",
      "dat": "Империи",
      "acc": "Империю",
      "ins": "Империей",
      "prep": "Империи"
    },
    "aliases": ["империя", "имперцы", "красные"],
    "gender": "f",
    "animate": false
  },
  "predicate:is_outlaw": {
    "lemma": "вне закона",
    "type": "predicate",
    "synonyms": ["незаконный", "преступный", "вне закона"],
    "valence": ["subject", "object"]
  }
}
```

Правило: **новое имя в контенте обязано иметь лексикон**, иначе агент
может о нём говорить только описательно. Линтер диалога проверяет
покрытие: каждая фракция, орган, работа, предикат и суть, упомянутые в
репликах, имеют словарную статью.

## 5. Разбор: конкретный план

### 5.1. Нормализация

* Unicode NFC, `ё → е` для поиска (но `ё` сохраняется в выводе);
* нижний регистр для лемматизации;
* разбиение на токены с учётом дефисов и чисел;
* определение границ предложения;
* исправление опечаток: расстояние Левенштейна по словарю, порог из
  данных, при неоднозначности — уточнение.

### 5.2. Грамматика

Типизированная грамматика с признаками:

* часть речи, падеж, число, род, одушевлённость;
* переходность, вид, время, наклонение;
* тип именной группы, тип вопроса.

Правила хранятся в JSON и компилируются в продукционную систему.
Парсер — chart/Earley с унификацией. Порядок обхода фиксирован,
поэтому результат детерминирован.

Пример правила (упрощённо):

```json
{
  "id": "clause_transitive",
  "lhs": "S",
  "rhs": ["NP:subj", "V:pred", "NP:obj"],
  "features": {
    "V:pred.case_obj": "acc",
    "NP:subj.agr": "V:pred.agr_subj"
  },
  "semantics": {
    "op": "apply",
    "predicate": "V:pred.sem",
    "args": ["NP:subj.ref", "NP:obj.ref"]
  }
}
```

Здесь видно главное: правило связывает **синтаксис** (порядок и
согласование) с **семантикой** (предикат и роли). Никакой вероятности:
если признаки унифицировались, правило применимо; порядок применения
задан списком.

### 5.3. Неоднозначность

Все разборы сохраняются, затем выбирается один по **явным правилам
предпочтения**:

1. больше связанных сущностей из текущего диалога;
2. более специфичная конструкция;
3. более короткое дерево;
4. лексикографический порядок правил (последний критерий).

Никаких скрытых весов. Если разборы действительно равнозначны,
система задаёт уточняющий вопрос — это честнее, чем угадывать.

### 5.4. Неизвестный ввод

Если разбор не удался:

* попробовать частичный разбор и извлечение сущностей;
* если найдена одна сущность и один тип вопроса — ответить с оговоркой;
* иначе — уточнение: «Не понял вопрос. Вы спрашиваете о Республике или
  об эдикте?»
* после двух неудач — предложить примеры допустимых вопросов (не меню
  ответов, а подсказку).

## 6. Вывод и объяснения

### 6.1. Типы ответов

| Тип | Пример | Механизм |
|---|---|---|
| Да/нет | «Считает ли Империя Республику незаконной?» | доказательство или контрмодель |
| Факт | «Какова легитимность Империи?» | прямой факт из BDI/активов |
| Список | «Какие органы повреждены?» | запрос с проекцией |
| Причина | «Почему?» | трассировка доказательства |
| Прогноз | «Что будет, если…?» | вывод по правилам, без симуляции |
| Незнание | «Где сейчас флот?» | отсутствие факта в модели агента |
| Уклонение | «Это государственная тайна.» | политика раскрытия |

### 6.2. «Почему» без магии

Ответ на «почему» — это **путь в графе доказательства**:

```
conflict(red, blue)
  ← belief(red, is_outlaw, blue, 0.8)
      ← work(imperial_edict, success, turn=2)
          ← ...
```

Планировщик выбирает 1–3 наиболее близкие и релевантные посылки.
Релевантность — детерминированная функция: прямота связи, свежесть,
упоминание в вопросе, ранг источника. Это не «объяснение нейросети»,
а реальная цепочка правил, которую можно распечатать.

### 6.3. Контрфактические вопросы

«Что было бы, если бы эдикт не издали?» — это не полная симуляция,
а **контрмодель**: временно убрать факт, пересчитать вывод, сравнить.
Границы: один-два шага, без побочных эффектов и без изменения кампании.
Если вывод не меняется — честно сказать «ничего бы не изменилось».

## 7. Личность, честность, отношения

Агент — не справочная. Данные личности задают:

* **регистр:** обращение, длина фраз, допустимая грубость;
* **политику раскрытия:** что говорит о своих планах, что скрывает;
* **темы-табу:** о чём отказывается говорить;
* **отношение к игроку:** доверие, страх, уважение;
* **цель разговора:** разведать, запугать, продать, затянуть время.

Пример:

```json
{
  "id": "abwehr_chief",
  "register": "military",
  "disclosure": {
    "default": "partial",
    "on_topic": {
      "military_plans": "withhold",
      "enemy_losses": "boast"
    },
    "lie_probability": 0.0
  },
  "taboo": ["personal_orders"],
  "address": "ваше величество"
}
```

`lie_probability` — не языковая статистика, а параметр персонажа. Но
даже ложь детерминирована: при заданном seed и политике выбирается
конкретная ложная пропозиция из допустимых, и в трассировке видно, что
это ложь.

Отношения влияют на **объём** и **тон**, но не на логическую истинность
вывода. Это важно: мир не меняется от того, что игрок неприятен агенту,
меняется лишь то, что агент готов сказать.

---

### 7.1. Связь с RL и символьной моделью

Диалог не заменяет RL и не спорит с ним. Разделение такое:

| Слой | Что делает | Чего не делает |
|---|---|---|
| RL / политика | Выбирает социальную стратегию: ответить, уклониться, соврать, пригрозить, потянуть время | Не выбирает факты и не пишет текст |
| Символьная модель | Хранит онтологию, убеждения, правила, геометрию, историю | Не «учится» на диалогах |
| Диалоговый планировщик | Строит план содержания из доказательства и политики | Не добавляет факты, которых нет в модели агента |
| Реализатор | Синтезирует русскую фразу | Не меняет логическую форму |

Политика может быть табличной (Q-table) или детерминированной функцией
полезности от символических признаков. В любом случае на выходе —
**социальное действие**, а не предложение текста. Если политика
обучена, её таблица/веса лежат в данных и проверяются тестами; в рантайме
нет скрытой нейросети. Ответ всё равно проходит через логический вывод,
поэтому «почему агент так сказал» объясняется и стратегией, и
доказательством.

Это же разделение позволяет менять баланс, не трогая язык: политика
делает агентов агрессивнее или осторожнее, а грамматика и лексикон
остаются прежними.

## 8. Детерминизм и отладка

### 8.1. Правила детерминизма

1. Никаких `set` в порядке обхода; только отсортированные списки.
2. Никаких временных меток и `id()` в результате.
3. Один seed на кампанию; диалог использует отдельный поток
   `dialogue_rng`, чтобы не сдвигать кампанийный RNG.
4. Фиксированный порядок правил, фактов и конструкций.
5. Ограничение глубины вывода и размера chart — константы в JSON.
6. При таймауте/лимите — не случайный ответ, а уточнение.

### 8.2. Инструмент `--debug-dialogue`

Для каждой реплики печатается:

```
Ввод:      Почему Империя считает Республику незаконной?
Токены:    почему / империя / считать / республика / незаконный
Разбор:    [дерево]
Логика:    question(why, belief(red, is_outlaw, blue, ?v))
Агент:     char_red_001 (Император)
Знание:    belief(value=0.8, source=edict, turn=2)
Вывод:     conflict(red, blue) ← belief(...) ← edict(...)
Акт:       explain
План:      kernel + 2 premises, stance=confident
Синтез:    [дерево реализации]
Ответ:     «Потому что эдикт объявил их мятеж незаконным...»
```

Любой шаг можно прогнать отдельно: `parse("...")`, `infer(form, agent)`,
`plan(form, proof, persona)`, `realize(plan)`. Это и есть белый ящик:
не «посмотрите на attention», а «посмотрите на конкретное правило».

## 9. Тестирование

| Тест | Что проверяет |
|---|---|
| Golden parse | Фраза → ожидаемое дерево и логическая форма |
| Paraphrase set | 5–10 формулировок одного вопроса дают одну форму |
| Round-trip | Синтез → повторный разбор даёт ту же пропозицию |
| Truthfulness | Ответ не противоречит BDI агента |
| Non-hallucination | Каждое имя/число в ответе есть в KB или лексиконе |
| Determinism | Два прогона с одним seed дают идентичный транскрипт |
| Unknown input | Мусор → уточнение, без исключения |
| Coverage | Каждая работа/орган/предикат имеют лексикон |
| Performance | Ответ за бюджет времени на слабом железе |
| Read-only | Диалог не меняет снимок кампании |

Отдельно — **инвариант отсутствия DSL**: в UI нет полей «предикат»,
«субъект», «объект»; только текстовая строка.

### D1.5. Композиционный синтез — выполнен

Ответ — не выбранный готовый текст, а **смысл**, собранный в
предложение. Путь:

1. План доказывает отношение и получает аргументы.
2. `synthesis.statements[отношение]` задаёт конструкцию и роли.
3. Конструкция — дерево частей: `np`, `lex`, `adj`, `number`, `text`,
   `literal`, `clause`, `address`, `items`, `marker`, `act`,
   `particle`.
4. `realize.py` собирает части, согласует род, число, падеж, время.
5. `morph.py` даёт словоформы; исключения — в
   `synthesis.word_forms`.

Что расширяется только JSON-ом: новое отношение, конструкция, сущность,
описание, коллекция, словоформа, роль адаптера.

`realization.json` сохранён как аварийный fallback; линтер требует
конструкции для всех предикатов убеждений и следит, чтобы новые
отношения не оставались без синтеза.

Границы D1.5 (осознанно):

* QUD, анафора, эллипсис и многорепликовая память — в D2.
* Агрегация нескольких пропозиций в одно сложное предложение —
  частично сделана в регистровом слое (см. ниже про `_clause`).
* Вариативность — структурная (разные конструкции в данных).
* `pymorphy3` — детерминированный словарь форм, не нейросеть.

### D2. Диалоговое состояние — выполнен для QUD, референтов, общего фонда, местоимений, эллипсиса и памяти партии

Два уровня состояния:

* `ConversationState` — текущий разговор: QUD, активные референты,
  местоимения, последний вопрос/ответ, общий фонд. Живёт в
  `DialogueSession`.
* `DialogueMemory` — долговременная память одного агента в одной партии.

`DialogueMemoryStore` хранит память по агентам (`speaker_id`), целиком
лежит в блоке `dialogue` сейва (версия 3), миграция 2 → 3 создаёт
пустой контейнер.

Данные `configs/dialogue/state.json`: местоимения, разрешение сущностей,
веса референтов, QUD, намерение вопроса, фрагменты (декларативный
эллипсис), уточнения, память, общий фонд.

Референты обновляются детерминированно: упоминание добавляет вес
позиции, каждый ход умножает на `decay_per_turn`, местоимение выбирает
самого весомого кандидата с совпадающим родом и числом.

Эллипсис — гибрид: полная фраза через chart-парсер, короткий фрагмент
через шаблоны `state.fragments`; правки пути логической формы задаются
JSON-ом. «А у Республики?», «Почему?», «А он?» восстанавливаются из
предыдущего хода.

Память хранит не транскрипт, а следы: сущности, значимые факты, общий
фонд, краткие сводки. Забывание детерминировано (затухание по игровому
времени, закрепление, лимиты по категориям).

Границы D2:

* Обязательства, обещания и угрозы не хранятся как речевые акты — D4.
* Сырые реплики не сохраняются.
* Новый вид слота фрагмента или новая операция правки формы требуют
  интерпретатора в `state.py`.

### D3. Объяснения и контрфакты — частично

Уже есть:

* «Почему» через трассировку (`_answer_explain`, `solution.proof.because`).
* Выбор посылки — по сработавшему правилу; расширенный выбор 1–3
  релевантных посылок — открыт.
* Сравнение и контрмодели («что если», «кто сильнее») — открыты.

### D4. Речевые действия — открыт

* Просьбы, приказы, обещания, угрозы, предложения.
* Проверка допустимости по должности и отношениям.
* Пока **без изменения мира**: агент отвечает «сделаю/не сделаю»,
  но эффект не применяется.
* Позже — узкий мост к кампании: диалог создаёт намерение, а не
  мгновенный эффект.

### D5. Продвинутый синтез — частично реализован в регистровом слое

Что уже в `realize.py` (сделано раньше формального этапа D5):

* регистровый выбор лексем (`_entry`, `_select`);
* выбор конструкции по признакам стиля (`_select`,
  `act_constructions`);
* вложенные клаузы (`_clause`, `conjunction`) — главное + придаточное;
* обращения как именные группы (`_address`, `address_mode` pre/post);
* дискурсивные маркеры и частицы (`_marker`, `_particle`);
* антиповтор через `avoid_recent` (`features.select_best`);
* трасса выбора (`_record`, `take_trace`) уходит в `Answer.data`
  (`construction`, `primary_construction`, `constructions`, `lexemes`,
  `register`).

Что ещё открыто:

* агрегация нескольких пропозиций в одно сложное предложение целиком
  (сейчас частично через `_clause`);
* порядок тема-рема;
* вариативность по детерминированному ключу контекста (сейчас —
  структурная, через данные).

* Больше типов вопросов и тем.

## 11. Стилевой слой (регистры)

Стиль — регистровый профиль реализатора, а не постобработка строки.
Данные: `configs/dialogue/styles.json` (schema 4, `neutral`,
`official`, `report`, `order`, `friendly`, `romantic`, `hostile`,
`mentor`), `configs/dialogue/features.json` (измерения и умолчания).

Код:

| Файл | Роль |
|---|---|
| `campaign/dialogue/style.py` | `StyleEngine`, `SELECTION_KEYS`, `features()`, `is_neutral()` |
| `campaign/dialogue/features.py` | `match_score`, `compatible`, `select_best`, `filter_compatible` |
| `campaign/dialogue/coverage.py` | отчёт покрытия актов, маркеров, обращений |
| `campaign/dialogue/loader.py` | `load_styles` с `extends`/`features`/`selection`, `load_features` |
| `campaign/dialogue/lint.py` | `_style_problems`: default, id, label, register, features, selection-ключи, `avoid_recent` |
| `campaign/dialogue/answers.py` | `set_style`, `Answer.data` с трассой |
| `campaign/dialogue/engine.py` | `set_style`, `_profile` |

Нейтральный стиль сохраняет прежний путь байт-в-байт
(`StyleEngine.is_neutral` → `realize_act` возвращает `fallback`).
Новый стиль добавляется только правкой `styles.json` (и, при новых
значениях признаков, `features.json`). Экран чата — `view/screens/
dialogue_chat.py`, вход — кнопка «СВЯЗЬ» в `automata_screen.py`.

Подробности архитектуры, диагноз отвергнутого первого подхода и решение
по объёму — в [`CHAT_STYLES_PLAN.md`](CHAT_STYLES_PLAN.md).

## 12. Риски и меры

| Риск | Мера |
|---|---|
| Грамматика разрастается и становится неподдерживаемой | Типизированные правила, модульность, тесты на парафразы |
| Комбинаторный взрыв разбора | Ограничения chart, beam по правилам, таймаут → уточнение |
| Морфология не покрывает имена | `pymorphy3` + `synthesis.word_forms`, линтер ссылок |
| Ответы звучат шаблонно | Регистровый реализатор: конструкции, лексемы, акты, маркеры, антиповтор |
| Новый домен требует правки Python | `world.adapter`, конструкции и поля в JSON, тест на новый домен |
| Агент «знает» больше, чем должен | эпистемический адаптер, тесты на незнание |
| Ложь выглядит как ошибка | трассировка помечает ложь, тесты политики |
| Диалог меняет мир незаметно | read-only по умолчанию, отдельный мост для действий |
| Недетерминизм из-за порядка словарей | сортировка, golden-тесты снимка |
| Игрок пишет вне домена | уточнение + подсказка, без падения |
| Стиль вырождается в шаблон | запрет `frames`/`prefix`/`suffix`, регистровый профиль, `coverage.py` |

## 13. Что считать успехом

Не «проходит тест Тьюринга». Успех прагматичный:

1. Игрок задаёт вопрос своими словами, не выбирая вариант.
2. Ответ следует из фактов и правил, а не из заранее написанной ветки.
3. На вопрос «почему» есть объяснимая цепочка.
4. Разные агенты отвечают по-разному в силу своих знаний и личности.
5. Всё воспроизводится и отлаживается без нейросетей.
6. Новый факт/работа/орган/стиль в JSON расширяет словарь и ответы без
   переписывания диалогового движка.

## 14. Открытые вопросы

1. **Границы домена.** Широкий лексикон, но содержательные ответы —
   только о мире игры.
2. **Морфологический анализатор.** `pymorphy3` как детерминированный
   словарь форм, лексикон — для доменных имён, `synthesis.word_forms` —
   для исключений.
3. **Связь с RL.** Политика выбирает социальную стратегию через
   детерминированную функцию выгоды от символических признаков.
   Нейросетевой политики нет.
4. **Действия через диалог.** Только намерение; эффект — через обычный
   конвейер работ.
5. **Память диалога.** Ограниченное окно + сводка в BDI, миграция схемы.
6. **Оценка естественности.** Субъективная, но проверяемая: корпус
   парафраз, blind-сравнение с шаблонами, отсутствие повторов.

## 15. Итоговая рекомендация

Идти гибридным путём **G**:

* разбор — типизированная грамматика с унификацией;
* содержание — логический вывод по эпистемической модели агента;
* объяснения — трассировка доказательства;
* синтез — композиционные конструкции с морфологией и регистровым
  профилем; `realization.json` — только fallback;
* детерминизм и отладка — обязательные контракты, а не «потом».

Начинать с D0–D1: узкий домен, read-only, вопросы о фактах и намерениях.
Это уже закрывает глубинную потребность «спросить агента своими словами
и получить осмысленный ответ», не нарушая ни одного ограничения.
