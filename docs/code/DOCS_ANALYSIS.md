## Этап 1. Иерархия истины и входные документы

### README.md (527 стр.) — витрина проекта
- **Назначение:** общая карта: что проект, как запустить, какие слои существуют.
  Разделы (фактически h1): инструменты (automata/organizations/naming/systems/
  interaction) → «Что» → «Математика» → «Состояние реализации (актуально)» →
  «Войсковые автоматы» → «Запуск» → «Графический слой» → «Новые слои (MVP)».
- **Ключевое:** ссылается на `docs/SOURCE_OF_TRUTH.md` как источник истины.
  Определение: «иерархическая мультиагентная марковская игра с частичной
  наблюдаемостью, структурированным символьным состоянием и RL». Дизайн-принцип —
  ТРИЗ-редукция («лучшая функция — та, которой нет»).
- **Математика (канон `simulation.py`):**
  `regen = floor(sqrt(force))`; `work <= min(pool, MAX_WORK, max(MIN_OUTPUT, force//4))`;
  `U(a) = delta + gamma*reward(t)`; триггер Шмитта `ON(F)=max(ON_MIN, ON_FRAC*F)`,
  `OFF(F)=OFF_FRAC*ON(F)`; открытый вход ~`w*m*GAIN_MAX`, закрытый ~`w*m*Y_SMALL`;
  отдых `rest_gain = MAX_REST_DELTA*(E/L)*(1-E/L)`, rest_units растут только от
  реально полученной силы.
- **Логика:** все сущности — IPO-автоматы (+BDI у персонажей); среда —
  «всеобъемлющий IPO-автомат»; две метрики сила/энергия; тип энергии —
  контекстная фаза; активные сцены используют `core41.ArenaAgent` (QTable+BDI).
- Разделы-визитки CLI слоёв: `--automata`, `-m organizations`, `-m naming`,
  `-m systems`, `--interaction`, warfare, кампания (`view/`, `world_actor`),
  арена/RL (`core41`, `agents`), новые слои MVP (lossy/LOD/entropy — выключены
  по умолчанию, канон `run_batch(10)` = `RL 1 / UtilityAI 9 / no capture 0`).
- Единая точка запуска `main.py` (`--view` — кампания); список тестов и
  экспериментов продублирован здесь же (см. также CONTRIBUTING).

### docs/SOURCE_OF_TRUTH.md (467 стр.) — главный канон
- **Роль (§1):** истина верхнего уровня; в репо одновременно текущий код
  (simulation.py — легаси-канон дуэлей, campaign/world.py, warfare, UI),
  целевая модель 4-2-1 и переходный период (core41/agents уже в активных
  сценах; кампания ещё не мигрирована). Текущий `WorldEngine` — НЕ ядро,
  а легаси-слой узких должностей/организаций.
- **Порядок при расхождении:** 1) решения/онтология — этот документ;
  2) детализация — `WORLD_CORE_MODEL.md`; 3) текущее поведение кода —
  `MODEL.md`/`BASELINE.md`/тесты; 4) текущая кампания — `WORLD.md`;
  5) история — `WORLD_MODEL_REVIEW.md`, `history/`.
- **Ядро 4-2-1:** `A_i = (I_i, O_i, H_i, S_i; F_i, E_i; W_i)` — входы, выходы,
  обработчики, состояния; сила, универсальная энергия, работа.
  Работа: `W = {amount, form, payload, duration}`; баланс
  `E_i -= amount; E_j += amount*efficiency(context); loss = amount*(1-eff)`.
- **Принятые решения (таблица §3):** одна универсальная энергия (типов нет);
  успех — логистическая сигмоида `p = sigmoid(β0 + β_skill·skill + β_auth·authority
  − β_res·resistance + β_ctx·context)`; отношения асимметричны (`R_ij ≠ R_ji`);
  BDI/не-BDI (без третьего типа); игрок — BDI-автомат под управлением человека;
  предметы без сознания → не BDI; время — бесконечная RTS по секундам,
  скорости pause/1x/2x/4x/8x/16x с автопрерыванием; победы нет — только
  поражения (смерть героя, распад организации: `power/cohesion ≤ 0.05`
  2 дня подряд, ноль — сразу); увольнение — смена роли, не поражение;
  старые шкалы (`wealth/power/legitimacy/cohesion/reach/capacity/standing`) —
  проекции ядра; текущий `WorldEngine` — легаси-частный случай, не ядро.
- **14 инвариантов (§5):** контекст важнее воздействия; нет изменений статистики
  без работы; нет бесплатных действий; одна энергия; F≠E; BDI только у сознающих;
  природа — не декорация; предметы/персонажи — автоматы; победы нет;
  асимметрия отношений; композиция; непрерывное время; наблюдаемость причин;
  старые шкалы — проекции.
- **Карта документации (§6)** — нормативное распределение ролей md-файлов
  (канон / текущая реализация / обзор / заморожено).
- **Правила изменений (§8):** сначала решение здесь, затем доки, затем код;
  нельзя молча менять код под документ или документ под код.
- **Открытые вопросы (§7):** единицы/потери E/F, экономика распада, рынок труда,
  граница управления игроком, коэффициенты логистики, миграция шкал,
  непрерывные внутридневные действия.
- **§9 Ближайший статус:** подробный лог завершённого (core41, здоровье H=100,
  болезнь sickness∈[0,1] + TREAT, контагиозность, SimulationClock, agents v2
  чекпойнты 21 признак, ArenaEnvironment, campaign/planner) и незавершённого
  (миграция кампании, устойчивые раны).

### docs/AGENTS.md (576 стр.) — слой обучаемых агентов
- **Роль:** спецификация `agents/` + RL-среза `core41`.
- **Структура:** §1 что работает (1.1 core41-дуэль; 1.2 здоровье/смерть/
  множители; 1.3 реальное время; 1.4 политики и адаптивный агент) → §2 что
  изменилось в игре → §3 как обучить политику (полный CLI) → §4 контракт
  наблюдения/действия (включая ёмкость и версии чекпойнтов, проблемы
  готовности №4–5) → §5 ограничения и следующий шаг.
- **Сигнатуры:** `BDIPolicy` (линейные веса 21×6, online-градиент, отдельные
  `campaign_weights` через `campaign_features()` — 21 признак), `QTablePolicy`
  (дискретизация наблюдения), `MLPPolicy` (tanh hidden=16, target-сеть, TD(0),
  без PyTorch, те же 21 признак), `PolicyAgent` (легаси-мост),
  `load_policy(path)` (автоформат), `checkpoints.py` (auto-find best→latest→
  свежий; битые файлы пропускаются). `CHECKPOINT_VERSION = 2`; миграции
  v0/v1→v2 дополнением нулями, QTable-ключи 8/10→12.
- **Окружения:** `ArenaEnv` (self-play, `with_env=True` по умолчанию —
  train/serve alignment), `DuelEnv`, `CampaignEnv` (`TREAT_SELF` −0.20 болезни,
  `target_mode="all"`, усечение горизонта = ничья). Награда арены: F/H
  нормированы, стоимость E = 0.6·ΔE/E_max, лечение +1.0·Δs, заражение
  +0.5·Δs, терминальные ±1.0.
- **CLI:** `python -m agents.train --episodes N --seed S [--env
  arena|duel|campaign] [--no-self-play] [--eval-episodes/--eval-opponents
  bdi,qtable,random,mlp] [--domain-randomize --profiles --sickness-min/max
  --health-min/max --health-factors --skill-jitter] [--save-best --best-every]
  [--resume]` ; held-out: Wilson CI `win_rate_ci`, прогрев baselines
  (`--eval-baseline-episodes`=50), `trained_episodes/policy_source`, кампанийная
  строка «политика против мира». `--max-steps`: arena=2000, duel=160,
  campaign=30.

## Поперечные наблюдения по документации

1. **Жёсткая иерархия истины.** SOURCE_OF_TRUTH задаёт приоритет; каждый
   документ имеет статус (канон / текущая реализация / обзор / заморожено /
   не источник истины). Противоречия разрешаются правилами §8 («сначала
   решение в каноне, затем доки, затем код»), а не «на глаз».
2. **Разделение «текущее vs целевое».** Пара MODEL.md (факт кода) ↔
   WORLD_CORE_MODEL.md (цель) проходит красной линией; активные сцены уже на
   цели (core41), кампания — на полпути, simulation.py — легаси-канон.
3. **Документация ↔ код связаны тестами:** `test_docs_sync.py` сверяет
   константы MODEL.md §8 с кодом; BASELINE привязан к test_canon.py и CI
   (`tests/test_checks.py` прогоняет exp-скрипты с кодом возврата 0/1).
   Документация — исполняемо-проверяемый артефакт; PR-чек-лист это закрепляет.
4. **Инварианты как дизайн-закон:** «нет бесплатных действий», «контекст
   важнее воздействия», «победы нет» — формулировки напрямую диктуют механику
   (стоимость E, обработчики, только defeat-условия).
5. **Каждый слой описан по одному шаблону:** роль → запуск/CLI → модель/API →
   архитектура пакетов → тесты → границы. Границы («чего слой НЕ делает») —
   обязательный раздел; так защищается канон simulation.py.
6. **История заморожена и маркирована** (status-шапки в docs/history/,
   experiments/history/, FIX_HYPOTHESIS): устаревшие численные «верификации»
   явно помечены невоспроизводимыми; каноническая механика никогда не
   выводится из отвергнутых PR-доков.
7. **Дублирование карты запуска** (README ↔ CONTRIBUTING ↔ эксперименты) —
   осознанное: README для пользователя, CONTRIBUTING для процесса,
   experiments/README для проверок.
8. **Пробелы:** SUMMARY/WORLD местами отстают от SOURCE_OF_TRUTH §9 (новые
   флаги CLI, версия чекпойнтов 2); TODO.md велик и частично превратился в
   журнал закрытых задач; DESIGN_ADVANCED не покрывает post-migration статус
   LOD; часть цифр (88 событий, 21+19 культур) продублирована в трёх местах
   и требует синхронизации при изменении конфигов.
