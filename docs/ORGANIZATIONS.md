# ORGANIZATIONS.md — аналитические организации-суперсистемы

> **Статус.** Чистое Python-ядро, runtime-слой и генератор JSON для редактора
> [`automata/`](../automata). Слой не импортирует pygame и не меняет канон
> `simulation.py`: боевой закон остаётся в `simulation.run_tick`, а runtime
> организаций подключается к `WarfareSimulation` опционально. Без
> `add_organization` поведение войны не меняется.

## 1. Что это

`organizations/` выводит организацию-суперсистему аналитически, а не выбирает
готовый шаблон:

* **приоритетная потребность** — одна из 16 канонических потребностей
  (`warfare.NEEDS`), как смесь приоритета массы и лидера;
* **масштаб удовлетворения** — из энергии участников и плотности связей;
* **уровень организации** — из эффективного числа участников и порога 165;
* **экономика участия** — организация живёт, пока есть участники, которым
  выгодно её существование; иначе она распадается;
* **универсальная функциональная цепь** — взносы → благо → распределение →
  принуждение/легитимация → воспроизводство участия;
* **ярлык** «государство», «церковь», «банда», «артель» — производная от
  доминирующей функции и уровня, а не отдельная механика.

Один и тот же код даёт государство при приоритете страха и большом масштабе,
церковную иерархию при приоритете духовности, банду при статусе и малом
масштабе, торговую артель при голоде/жажде. Различаются параметры и названия
состояний, а не набор захардкоженных классов.

## 2. Вход модели

```python
Member(
    id="m001",
    needs={"fear": 0.85, ...},   # неудовлетворённость 0..1, 16 потребностей
    urgency={...},               # вес потребности личностью; по умолчанию = needs
    energy=1.0,                  # energy_pool персонажа
    force=1.0,                   # force персонажа
)
Population(members=[...], links=[("m001", "m002", 0.8), ...])
```

Для больших однородных сценариев не нужно материализовать все рёбра:

```python
Population.complete(members, weight=0.85)   # плотность 0.85 без списка рёбер
```

Адаптер к существующему персонажу:

```python
member = Member.from_character(character)
# needs = character.needs
# urgency = character.weighted_urgency()
# energy = character.energy_pool
# force = character.force
```

`Member.urgency` влияет на **приоритет** потребности (BDI-слой), а
`Member.needs` — на **выгоду участия** (размер нужды). Это не добавляет новых
метрик в `Agent.state`: сила и энергия остаются двумя каноническими метриками.

## 3. Масштаб и уровни

Для активного множества из `N` участников и взвешенного графа связей:

```text
ρ      = 2 · Σ w_ij / (N · (N − 1))          # плотность, 0..1
N_eff  = N · ρ                               # эффективное число участников
S      = N_eff · mean(energy)                # масштаб удовлетворения
L      = ceil(sqrt(N_eff / 165))             # уровень организации
cap(L) = 165 · L²                            # ёмкость уровня
```

Для `N = 1` плотность принимается равной 1 (одна связь не нужна); для пустого
множества `N_eff = 0`, `L = 0`, организация распалась.

| Уровень | Эффективных участников | Ёмкость |
|---|---|---|
| 1 | `0 < N_eff ≤ 165` | 165 |
| 2 | `165 < N_eff ≤ 660` | 660 |
| 3 | `660 < N_eff ≤ 1485` | 1485 |
| … | … | `165·L²` |

**Почему 165.** Это калибровочная точка, в которой координационная энтропия
начинает расти быстрее силы лидера. В первой итерации она не считается
отдельным runtime-показателем: равенство `dH/dN = dF_leader/dN` при `N = 165`
имеет замкнутое следствие `L ~ sqrt(N_eff/165)`. Если позже понадобится
диагностика, `H` и `F_leader` можно добавить как наблюдаемые, не меняя закон
уровня.

## 4. Приоритетная потребность: лидер + масса

Для каждой потребности `p`:

```text
w_i          = energy_i · (1 + 0.5 · centrality_i)
π_mass[p]    = Σ_i w_i · urgency_i[p] / Σ_i w_i
π_leader[p]  = urgency_leader[p] / Σ_q urgency_leader[q]
π[p]         = (1 − λ) · π_mass[p] + λ · π_leader[p]
priority     = argmax_p π[p]
```

`λ = 0.35` по умолчанию: масса задаёт основную повестку, лидер сдвигает её, но
не монополизирует. `λ` настраивается в `OrganizationParameters`; при `λ = 0`
получается чистая масса, при `λ = 1` — чистый лидер. Тай-брейк идёт по
каноническому порядку `NEEDS`.

Центральность — относительная взвешенная степень:
`centrality_i = strength_i / max(strength)`.

## 5. Универсальные функции и ярлыки

Семь функций не являются классами организаций:

| Функция | Что производит |
|---|---|
| `order` | безопасность, принуждение, закон |
| `meaning` | смысл, ритуал, авторитет |
| `provision` | продовольствие, воду, отдых, снабжение |
| `status` | ранги, престиж, доступ |
| `knowledge` | знание, обучение, мастерство |
| `care` | заботу, взаимопомощь, воспроизводство |
| `exchange` | обмен, взносы, рынок |

Веса функций:

```text
m_k = normalize( Σ_p π[p] · A[k, p] + (L − 1) · B[k] )
```

`A` — семантические коэффициенты потребности (например, страх тяготеет к
`order`, духовность — к `meaning`, голод/жажда — к `provision`), `B` —
небольшой сдвиг к управленческим функциям с ростом уровня. Это не таблица
готовых организаций: одна и та же формула даёт разные структуры при разных
`π` и `L`.

Ярлык выбирается по доминирующей функции и уровню:

| Доминанта | Уровень 1 | Уровень 2 | Уровень 3+ |
|---|---|---|---|
| `order` | банда | военный отряд | государство |
| `meaning` | секта | поместная церковь | церковная иерархия |
| `provision` | торговая артель | торговая компания | торговая лига |
| `status` | банда | клан | сословная иерархия |
| `knowledge` | кружок | школа | академия |
| `care` | касса взаимопомощи | община | система попечения |
| `exchange` | артель | гильдия | торговый союз |

Потребность задаёт конкретное благо: страх — безопасность, духовность — смысл,
голод — продовольствие, статус — статус и т.д. Полный словарь — в
`organizations/needs.py` (`NEED_GOODS`).

## 6. Экономика участия

Для участника `i`:

```text
d_i    = Σ_p π[p] · needs_i[p]                     # спрос на приоритетные блага
Q      = service_quality(L, mode_weights)          # качество благ
B_i    = d_i · Q · (1 + 0.25 · centrality_i · ρ)   # выгода
C_i    = contribution_rate · (0.5 + 0.5·e_i/mean_e) # взносы
K_i    = 0.06 · m_order · (1 − 0.5·legit)
         · (1 − 0.5·centrality_i)                  # риск принуждения
R_i    = 0.08 · (m_status + m_order)  (лидеру)     # рента лидера
O_i    = max(0, 0.30·d_i − 0.20·d_i·max(m))        # внешняя альтернатива
Δ_i    = B_i − C_i − K_i + R_i − O_i
```

Участник **желающий**, если `Δ_i ≥ 0` и `d_i > 0`. Принуждение не создаёт
желания: оно входит как риск `K_i`; безопасность/порядок входит как выгода `B_i`
через `Q` и `d_i`. Поэтому государство может держаться не только на страхе
перед властью, но и на страхе перед анархией — если выгода безопасности
перевешивает налоги и риск.

Коэффициенты `Q`, `contribution_rate`, `legit` выводятся из режимов:

```text
legit = clamp(0.5·m_meaning + 0.3·m_order + 0.2·m_status)
Q     = clamp(0.40 + 0.10·(L−1)
              + 0.25·legit + 0.15·m_provision
              + 0.10·m_care + 0.15·m_status)
r     = 0.05 + 0.12·m_order + 0.03·m_status + 0.04·hierarchy
```

**Fixed point участия.** Сначала активны все. Считаются метрики, затем
удаляются нежелающие; для нового активного множества метрики пересчитываются.
Процесс повторяется до устойчивого множества. Если не осталось ни одного
желающего — организация распадается (`dissolved = True`, `L = 0`). В одной
итерации выход односторонний: вышедший не возвращается. Это делает анализ
детерминированным и завершаемым; повторный вход — параметр runtime
(`allow_rejoin`), рекрутинг новых участников — следующая задача.

## 7. Автомат организации

Активная организация получает одну и ту же функциональную цепь:

```text
Потребность
   → Мобилизация (взносы)
   → Производство блага
   → Распределение
   → Принуждение (при уклонении)
   → Легитимация (оправдание принуждения)
   → Воспроизводство участия
   → обратно к мобилизации
```

Плюс кризисная ветка:

```text
Воспроизводство → Кризис участия → (реформа | распад)
```

Названия состояний подставляются из разбора. Для государства при страхе:

* «Мобилизация: налоги, трудовая и воинская повинность»;
* «Производство: безопасность»;
* «Принуждение: аппарат принуждения»;
* «Легитимация: законодательство»;
* «Воспроизводство: подготовка пополнения».

Для церковной иерархии при духовности:

* «Мобилизация: десятина и пожертвования»;
* «Производство: смысл»;
* «Принуждение: церковная дисциплина»;
* «Легитимация: догматика и авторитет»;
* «Воспроизводство: воспроизводство клира».

Переходы получают свободные текстовые `event`/`guard`; редактор их не
интерпретирует, но они показывают условия (доля приоритета, ставка взносов,
доля желающих, уклонение, кризис). Если желающих нет, генерируется минимальный
автомат из двух состояний: «Потребность: …» → «Распад: нет желающих».

Сгенерированные файлы используют `version = 1`, уникальные `id`, одно начальное
и хотя бы одно финальное состояние; `Automaton.validate()` для них пуст.

## 8. Runtime-слой

`organizations/runtime.py` превращает срез в такт. `OrganizationRuntime` —
наследник `simulation.Environment` (суперсистема с `members` и `snapshot()`), но
его `tick()` не вызывает канонический `Environment.tick`: бой по-прежнему
делает `WarfareSimulation`, а организация живёт после боя.

```python
import warfare as W
from organizations import OrganizationRuntime

det = W.Detachment("линия", "red", [
    W.Character("боец-1", "red", seed=1),
    W.Character("боец-2", "red", seed=2),
])
sim = W.WarfareSimulation(seed=7, turns=20)
sim.add_detachment(det)

org = OrganizationRuntime("государство", "red", detachments=[det])
sim.add_organization(org)
sim.run()

print(sim.summary()["organizations"])
```

За такт runtime:

1. собирает `Population` из живых персонажей текущего среза (потребности,
   `weighted_urgency()`, `energy_pool`, `force`);
2. строит граф: по умолчанию — полный с весом `complete_weight` (0.8), либо
   явные `links` по id участников;
3. вызывает тот же `OrganizationSolver`, что и аналитический CLI;
4. исключает нежелающих (по умолчанию выход односторонний; `allow_rejoin=True`
   разрешает повторный вход) и распускает организацию, если желающих нет;
5. применяет мягкие эффекты к **существующим** полям персонажа: закрывает
   потребности по приоритету и функциям, добавляет усталость/голод за взнос,
   страх/тревогу за риск принуждения, мораль за легитимацию и ренту лидера;
6. после эффектов обновляет психологию отделений и возвращает снимок с
   событиями такта.

Фазы (`phase`) — наблюдаемая проекция универсальной цепи:
`mobilizing → producing → distributing → enforcing/legitimating → reproducing`.
`crisis` включается при доле желающих ниже 50 %, `dissolved` — после распада.
Это не новые метрики `Agent.state`: фаза и события живут в runtime-объекте.

Ключевые параметры:

| Параметр | По умолчанию | Смысл |
|---|---:|---|
| `complete_weight` | `0.8` | плотность полного графа без явных связей |
| `links` | `None` | явные рёбра `(id, id, weight)` |
| `leader_id` | `None` | закрепить лидера по id/имени |
| `apply_effects` | `True` | только анализ, без изменения персонажей |
| `satisfaction_per_tick` | `0.03` | сила закрытия потребностей за такт |
| `contribution_cost` | `0.08` | усталость/голод за взнос |
| `coercion_factor` | `0.5` | перевод риска принуждения в страх |
| `allow_rejoin` | `False` | односторонний выход или повторный вход |

`tick()` возвращает `snapshot()` плюс `events` этого такта; `snapshot()` —
устойчивый снимок для `WarfareSimulation.summary()`, `public_snapshot()` —
срез без точных весов и identity вышедших.

Быстрый прогон реального warfare-сценария с одной организацией:

```bash
python3 -m organizations --runtime --turns 12
```

```python
from organizations import build_runtime_demo

sim, org = build_runtime_demo(seed=7, turns=12)
summary = sim.run()
print(summary["organizations"][0])
```

`WarfareSimulation.add_organization(org)` вызывает социальный такт после
`_after_fight()` и до проверки победы. События `organization`,
`organization_exit`, `organization_crisis`, `organization_dissolved`
попадают в общий журнал, а `summary()["organizations"]` содержит снимки.
Если организации не добавлены, список пуст и поведение симуляции не меняется.

## 10. Эталонные сценарии

`python3 -m organizations` выводит. `N₀` — исходное население, `N_active` —
желающие после fixed point; `N_eff = N_active · ρ`:

| Сценарий | N₀ | N_active | ρ | N_eff | L | Потребность | Доминанта | Ярлык |
|---|---:|---:|---:|---:|---:|---|---|---|
| `state_fear` | 900 | 811 | 0.85 | 689.4 | 3 | страх | порядок | государство |
| `church_spirituality` | 900 | 856 | 0.80 | 684.8 | 3 | духовность | смысл | церковная иерархия |
| `gang_status` | 80 | 73 | 0.90 | 65.7 | 1 | статус | статус | банда |
| `trade_artel_hunger` | 120 | 109 | 0.85 | 92.6 | 1 | голод | снабжение | торговая артель |

В каждом сценарии часть участников — «свободные ездоки» с нулевыми
потребностями. Они не получают выгоды и выходят, поэтому доля желающих меньше
100 %: это не декорация, а работа fixed point участия.

Один и тот же приоритет при разном масштабе даёт разные ярлыки: духовность при
`N_eff = 24` — «секта», при `N_eff = 684.8` — «церковная иерархия». Это
проверяется тестом, а не таблицей в коде.

## 12. Границы

* 165 — калибровочная константа; явная формула энтропии/силы лидера не
  считается в runtime.
* `λ = 0.35`, коэффициенты `A`, `B`, `Q`, `r` — калибруемые входы модели, а не
  эмпирически измеренные законы.
* Анализ одного среза статичен: это fixed point участия на текущем населении.
  Runtime повторяет срез каждый такт, но не создаёт новых персонажей, не
  рекрутирует вышедших и не моделирует миграцию между организациями.
* Одна организация на население; конкуренция организаций, внешний враг и
  обратная связь легитимности — следующие задачи.
* Runtime-эффекты намеренно мягкие и используют только существующие
  потребности/мораль/BDI-поля. Новых полей в `Agent.state` нет; организация
  остаётся опциональной надстройкой.
* Ярлыки иллюстративны: «государство» не является отдельным шаблоном с
  захардкоженными состояниями. Любая комбинация режимов и уровня даёт свою
  структурную цепь.
* Сгенерированные JSON можно открыть и править в `automata/`; повторный
  `--write` перезаписывает одноимённые slug'и.
