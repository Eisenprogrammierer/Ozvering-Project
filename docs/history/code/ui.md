# `ui`

Справочник собран из docstrings и примечаний к переменным. Номера строк относятся к версии до очистки кода.

## `ui/__init__.py`

### Модуль

Строка 1.

Сценный (экранный) слой 2-D интерфейса Ozvering-Project.

Пакет надстраивается над ``game_engine.py`` (который остаётся слоем «основное
игровое поле» — арена и HUD партии) и добавляет традиционную «игру»:

  * главное меню, настройки, экран сохранений/автосохранений, нарративные
    экраны, поле боя, доменно-нейтральные взаимодействия, экран «об игре»,
    оверлей паузы;
  * навигацию между экранами (стек сцен, ``ui.scene.SceneManager``);
  * систему сохранений и настроек (``ui.save.SaveManager``, JSON в ``saves/``);
  * плейсхолдеры вместо ассетов (``ui.theme.draw_placeholder``).

Модуль НЕ импортирует pygame на верхнем уровне, чтобы ``ui.save`` и
``ui.content`` были доступны и тестируемы без графической зависимости; pygame
требуется только для ``ui.scene``/``ui.widgets``/``ui.app`` и подпакета
``ui.scenes``.

Точка входа: ``python -m ui``.

## `ui/battlefield.py`

### Модуль

Строка 1.

Стратегический слой RTS + ролевой отыгрыш — чистая логика без pygame.

Зачем отдельный модуль: экранное поле (``ui/scenes/battlefield.py``) должно
рисовать изометрическую сетку, приказы и диалоги, но его логика обязана
тестироваться без графической подсистемы. Здесь нет импорта pygame: только
``simulation`` (публичное API) и стандартная библиотека.

Стратегическая специфика:
  * изометрическая сетка 11x9, выбор юнита, приказ движения по правому клику;
  * один командир на сторону; контакт (соседняя клетка) открывает приказы
    атаки, иначе доступны только движение/покой/удержание;
  * очки команд (CP) — тактический ресурс UI-слоя; бой считается моделью
    ``simulation.run_tick``, поэтому канон не меняется;
  * цель (высота) даёт CP и мораль, но не трогает физику модели.

Ролевой слой:
  * профиль командира (``CANON``/``ORTHODOX``/``ZEALOT``) выбирается в диалоге;
  * мораль, черты и репутация — UI-переменные, не метрики модели;
  * диалоги двуязычны (ru/en), как и остальной сценный слой.

## `ui/save.py`

### Модуль

Строка 1.

Система сохранений и настроек сценного слоя.

Всё хранится в каталоге ``saves/`` (в корне репозитория, в ``.gitignore``):
  * ``settings.json``           — пользовательские настройки;
  * ``autosave.json``           — автосохранение;
  * ``slot_1..3.json``          — ручные слоты.

Запись атомарная (временный файл + ``os.replace``), кодировка UTF-8. Битый или
отсутствующий JSON не роняет приложение: чтение возвращает ``None`` и пишет
предупреждение в переданный логгер.

Прогресс партии сериализуется как метаданные (seed, такт, победитель). Само
состояние партии не сохраняется: движок детерминирован по seed, поэтому позиция
восстанавливается повторным проигрыванием до сохранённого такта
(``game_engine.GameApp.start_match``).

## `ui/scene.py`

### Модуль

Строка 1.

Базовый класс сцены (экрана) и менеджер навигации между сценами.

Стек сцен: ``go`` меняет «корневой» экран, ``push``/``pop`` накладывают и
снимают экран-оверлей (например, пауза поверх партии). Экземпляры сцен в стеке
сохраняются, поэтому партия продолжается после снятия паузы.

Модуль не зависит от pygame: сцены получают события уже разобранными из
``ui.app``. Это позволяет тестировать навигацию без графической подсистемы.

## `ui/scenes/interaction.py`

### Модуль

Строка 1.

Экран доменно-нейтрального взаимодействия: объект → действие → исход.

Три панели соответствуют трём вопросам игрока:

* слева — **с кем можно взаимодействовать** (``Target``);
* в центре — **что с ними можно сделать**; панель раскрывается после выбора
  объекта;
* справа — **что может произойти**; прогнозы шумные, с диапазонами и
  неизвестными исходами.

Сцена только рисует и раздаёт ввод. Вся логика выбора, прогнозов и
детерминированного розыгрыша находится в ``interaction.model``.
