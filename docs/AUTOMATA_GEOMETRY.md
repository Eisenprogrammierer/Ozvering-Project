# Семантическая геометрия автоматов

> **Статус:** первый этап гибрида реализован (`campaign/geometry.py`,
> тесты `tests/test_geometry.py`). Этапы C/D и относительное время
> отложены осознанно.
>
> **Назначение.** Документ фиксирует, что такое геометрия мира в
> Data-Driven ядре, почему она не сводится к глобальным координатам и как
> контент задаёт расстояния, углы и ориентацию одними JSON-данными.

---

## 1. Задача

Кампания автоматов должна уметь отвечать на вопросы:

* как далеко один орган от другого;
* под каким углом к соседям он расположен;
* как разворачивается направление на дальнюю цель;
* сколько времени занимает путь по сети.

При этом мир не обязан иметь одну абсолютную систему координат. Более
того, глобальная сетка противоречит лору и целевой модели: пространство
относительно, у разных узлов свои локальные окрестности, а «дальнее»
направление зависит от выбранного пути.

## 2. Почему не глобальные координаты

Глобальные `x/y` удобны редактору и отрисовке, но опасны как источник
истины:

* они навязывают плоскую евклидову метрику там, где нужна сетевая;
* они делают расстояния и углы функцией от положения в редакторе, а не
  от связей мира;
* при переходе к локальным базисам (этап C) глобальные оси приходится
  выбрасывать, а вместе с ними — весь контент, который на них опирался.

Поэтому в ядре действует правило:

> **`layout.x/y` — только проекция для редактора и отрисовки.**
> Игровые расчёты читают длины рёбер, порядок соседей, углы поворотов и
> длительности, но никогда — координаты.

`MetricGraph` игнорирует ключ `layout` целиком. Тест
`test_layout_is_not_part_of_semantics` это фиксирует.

## 3. Этапы гибрида

| Этап | Что появляется | Статус |
|---|---|---|
| **A** | Координаты + евклидовы расстояния | не используется как семантика |
| **B** | 2D-метрический граф: длины рёбер, циклический порядок соседей, углы поворотов | **реализован** |
| **C** | Локальные базисы, переносы вдоль путей, голономия | отложен |
| **D** | Локальные часы, причинность, радарная дистанция | отложен |
| **E** | Масштабная/вейлевская относительность | опционально позже |

Этап B уже даёт содержательную игру: расстояния не хранятся, а
складываются по кратчайшему пути; углы локальны; дальние направления
разворачиваются вдоль геодезической. Этап C заменит усреднённую
плоскую композицию на честные переносы базисов, не меняя формат данных:
длины, порядок и повороты останутся теми же.

## 4. Модель этапа B: метрический граф

### 4.1. Узлы

Узел — это автомат: орган, подфракция или иное именованное состояние.
У узла **нет координат**. Есть только:

* `id`;
* набор инцидентных рёбер;
* циклический порядок полуребёр;
* угол поворота от каждого полуребра к следующему.

### 4.2. Рёбра

Ребро ненаправленное. Оно хранит:

| Поле | Смысл |
|---|---|
| `from`, `to` | концы ребра |
| `length` | локальная длина, `> 0` |
| `duration` | необязательная длительность, `>= 0` |
| `kind` | тип связи, по умолчанию `spatial` |

Внутренний ключ ребра канонический: `edge_key(a, b) == "a|b"` при
сортировке концов. Это делает данные и снимки стабильными независимо от
порядка объявления.

### 4.3. Ориентация

Ориентация узла — список соседей в порядке обхода и углы между соседними
полуребрами:

```json
"orientation": {
  "imperial_staff": [
    {"to": "abwehr",        "turn": 1.2},
    {"to": "cathedral",     "turn": 0.8},
    {"to": "guard",         "turn": 1.4},
    {"to": "justice",       "turn": 0.9},
    {"to": "propaganda",    "turn": 1.3},
    {"to": "wehrmacht",     "turn": 1.6}
  ]
}
```

Свойства:

* `turn` — угол **от текущего соседа к следующему по списку**, а не
  абсолютный пеленг;
* сумма поворотов вокруг плоского узла равна `2π`;
* если `turn` не указан ни у одного соседа, углы распределяются
  равномерно;
* если `turn` указан, он должен быть указан у всех соседей;
* узел степени 1 получает один поворот `2π`;
* узел степени 2 с двумя поворотами `π` означает «прямой проход».

Именно цикличность важна: без неё нельзя отличить узел, где путь идёт
прямо, от узла, где он поворачивает.

### 4.4. Единицы углов

Блок может задать `"angle_unit": "radian"` (по умолчанию) или
`"degree"`. Внутри ядра углы всегда радианы. Смена единицы не меняет
семантику данных, только их запись.

### 4.5. Схема

```json
{
  "schema": 1,
  "model": "metric_graph",
  "dimension": 2,
  "composition": "shortest_path",
  "angle_unit": "radian",
  "default_length": 1.0,
  "default_duration": 0.0,
  "edges": [
    {"from": "staff", "to": "field", "length": 2.0, "duration": 4.0}
  ],
  "orientation": {
    "staff": [{"to": "field", "turn": 6.283185307}]
  }
}
```

Поддерживаются два взаимно исключающих способа задать рёбра:

* `edges` — явный список с длинами;
* `lengths` / `durations` — карты `"a|b" -> число` поверх связей,
  взятых из `links` органов.

Одновременно `edges` и `lengths` задавать нельзя: это ошибка данных.
Неизвестные ключи, включая `layout`, игнорируются.

## 5. Запросы

`MetricGraph` — единственный источник истины. Публичный API:

| Метод | Результат |
|---|---|
| `length(source, target)` | длина ближайшего ребра или `None` |
| `duration(source, target)` | длительность ближайшего ребра или `None` |
| `neighbors(node)` | соседи в циклическом порядке |
| `edge(source, target)` | объект ребра или `None` |
| `degree(node)` | число соседей |
| `angle(node, source, target)` | меньший локальный угол, `[0, π]` |
| `signed_angle(node, source, target)` | знаковый поворот, `(-π, π]` |
| `turn(node, incoming, outgoing)` | поворот пути; прямой проход = `0` |
| `curvature(node)` | дефицит угла `2π − Σturn`; для плоского узла `0` |
| `nearest(node)` | соседи с длиной, длительностью и типом |
| `path(source, target)` | канонический кратчайший путь |
| `distance(source, target)` | длина кратчайшего пути или `inf` |
| `travel_time(source, target)` | сумма длительностей пути или `inf` |
| `angle_between_targets(observer, a, b)` | угол между направлениями на две цели |
| `validate()` | список проблем; для собранного графа пуст |
| `to_dict()` | нормализованное представление |

### 5.1. Локальный угол

`angle(node, source, target)` складывает `turn` по кратчайшей дуге
циклического порядка и возвращает меньший угол. `signed_angle` сохраняет
направление обхода. Это чисто локальная величина: она не зависит от
глобальных осей и от того, где узел нарисован.

`turn` удобен для движения: он отвечает не «под каким углом стоят два
соседа», а «насколько повернул путь, войдя из `incoming` и выйдя в
`outgoing`». Прямой проход — `0`, поворот на 90° — `±π/2`.

### 5.2. Дальнее расстояние

Дальнее расстояние **не хранится**. Оно равно сумме длин рёбер
кратчайшего пути. Поиск — детерминированный Dijkstra; при равной длине
пути сравниваются лексикографически по последовательности узлов, затем по
ключам рёбер. Поэтому результат не зависит от порядка словаря, платформы
или seed.

Если пути нет, `distance` возвращает `math.inf`, а `path` — `None`.

### 5.3. Дальнее направление

Дальний пеленг разворачивается вдоль канонического пути как
последовательность локальных поворотов:

```text
bearing = Σ turn(узел, предыдущий, следующий)
```

Для пути из одного ребра пеленг равен `0`. Это **плоская композиция**
этапа B: она усредняет переносы и не различает голономию. В графе с
циклами разные геодезические могут дать разные углы; ядро фиксирует один
канонический путь `shortest_path` и тем самым остаётся детерминированным.
Это документированное поведение, а не ошибка: честные переносы базисов —
задача этапа C.

`angle_between_targets(observer, first, second)` берёт первые шаги
канонических путей и складывает локальный угол с разностью их пеленгов.
Если хотя бы одного пути нет, возвращается `None`.

### 5.4. Длительность

`duration` ребра принимается и складывается в `travel_time`, но **пока не
является физическим временем**. Это метаданные для будущих локальных
часов. Глобальный `turn` кампании — планировщик вне мира, а не
абсолютное время.

## 6. Сборка из данных

### 6.1. Явная геометрия

Если у фракции есть блок `geometry`, он читается через
`MetricGraph.from_record(..., source="declared")` и валидируется
полностью. Любая ошибка — это `AutomataCampaignError` при создании
кампании, а не молчаливый откат.

Узлы обязаны соответствовать органам фракции. Ребро на неизвестный узел,
петля, повторяющееся ребро, нулевая/отрицательная длина, несовпадение
`orientation` со связями, сумма поворотов не `2π` — всё это громкие
ошибки.

### 6.2. Совместимый режим

Если блока `geometry` нет, граф собирается из `links()` органов
(`MetricGraph.from_links`, `source="derived"`):

* топология — связи органов;
* длина каждого ребра — `default_length`;
* ориентация — равные углы в порядке соседей.

Так работают старые пресеты и тестовые фикстуры. Режим не описывает
реальные расстояния, но сохраняет работоспособность кампании.

### 6.3. Где живёт производственная геометрия

Для лорных фракций геометрия лежит **на верхнем уровне**
`configs/campaigns/base/lore_factions.json` в ключе `geometry`, по
сторонам:

```json
"geometry": {
  "red": {"schema": 1, "model": "metric_graph", ...},
  "blue": {...},
  "green": {...},
  "amber": {...}
}
```

`campaign/preset.py` при загрузке шаблона копирует блок нужной стороны в
запись фракции (`setdefault`, поэтому локальный блок шаблона имеет
приоритет). Дальше `_build_geometry()` в `campaign/automata.py` строит
`MetricGraph` и кладёт его в `FactionRuntime.geometry`.

Разделение уровней намеренное: топология органов и их связи остаются в
`factions.<side>.organs`, а геометрические инварианты — отдельным слоем,
который можно править, не трогая работы и посты.

## 7. Кампания и условия

`AutomataCampaign` предоставляет:

| Метод | Смысл |
|---|---|
| `geometry(side)` | `MetricGraph` стороны или `None` |
| `geometry_distance(side, a, b)` | кратчайшее расстояние |
| `geometry_path(side, a, b)` | канонический путь |
| `geometry_angle(side, node, a, b)` | локальный угол |
| `geometry_bearing(side, observer, a, b)` | угол между целями |

Движок условий понимает два новых вида клауз:

```json
{"kind": "distance", "from": "staff", "to": "field", "op": "<=", "value": 2.0}
{"kind": "angle", "node": "staff", "from": "field", "to": "rear", "op": ">", "value": 0.5}
```

`distance` читает кратчайший путь, `angle` — локальный угол. Оба вида
требуют соответствующих полей: линтер проверяет `from`/`to` для
`distance` и `node`/`from`/`to` для `angle`.

## 8. Линтер и диагностика

`campaign/content_lint.py`:

* проверяет `factions.<side>.geometry`, если блок вложен во фракцию;
* проверяет верхнеуровневый `geometry.<side>` против органов этой
  стороны;
* принимает в качестве узлов органы подфракций;
* сообщает об ошибках схемы, модели, размерности, композиции, длин,
  ориентации и ссылок.

Запуск:

```bash
venv/bin/python -m campaign.content_lint
```

## 9. Детерминизм

Контракт этапа B:

* узлы и рёбра обходятся в отсортированном порядке;
* ничьи кратчайших путей разрешаются лексикографически;
* ориентация хранится кортежами;
* `to_dict()` округляет значения до 9 знаков и сортирует рёбра;
* `curvature` гасит численный шум в пределах `1e-6`.

Одинаковые JSON-данные дают одинаковые расстояния, пути и пеленги на
любой платформе.

## 10. Что отложено и почему

### 10.1. Этап C: локальные базисы

Сейчас дальний пеленг — сумма поворотов в одной усреднённой плоскости.
На этапе C появятся:

* базис в каждом узле;
* перенос базиса вдоль ребра;
* голономия вокруг циклов;
* различие «путь A» и «путь B» не только по длине, но и по переносу.

Формат данных менять не придётся: длины, порядок и повороты уже
достаточны. Добавятся необязательные поля переносов.

### 10.2. Этап D: часы и причинность

`duration` станет локальным временем ребра, появятся:

* собственные часы узлов;
* причинные конусы;
* радарная дистанция (время туда-обратно);
* согласование событий без глобального «сейчас».

До этого `travel_time` — только сумма метаданных.

### 10.3. Масштабная относительность

Масштаб/вейлевская относительность (этап E) — опциональное расширение:
локальные единицы длины могут зависеть от узла. Она не нужна для
текущей игры и не должна усложнять формат раньше времени.

## 11. Как добавить геометрию фракции

1. Перечислите органы и их `links` — топология уже есть.
2. Соберите `edges` с осмысленными длинами. Не обязательно рисовать
   координаты: длина — это стоимость/дистанция связи, а не метры на
   экране.
3. Для каждого узла задайте `orientation`: порядок соседей и `turn`
   между соседними полуребрами. Сумма поворотов — `2π`.
4. Убедитесь, что каждый сосед из `links` присутствует в ориентации.
5. Запустите линтер; ошибки данных должны быть исправлены, а не
   обойдены.
6. При необходимости добавьте `duration` для будущего времени, но не
   используйте его как физическое время в правилах.

## 12. Тесты

* локальные расстояния и углы;
