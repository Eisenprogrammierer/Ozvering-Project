## 0. Решение и границы

### 0.1. Решение

Принимается целевая модель канона:

> **Именованные работы остаются как шаблоны возможностей (capabilities).
> Эффект работы вычисляет обработчик получателя из контекста. Энергия —
> одна. Все слои используют один конвейер `Work`.**

Это не «одна универсальная работа вместо 65» и не удаление контента.
Наоборот: 65 работ, 17 взаимодействий и действия мира сохраняются как
авторские возможности с названиями, органами, ценой, кулдауном и UI. Меняется
только источник результата: не `effects` в записи, а `H_j` получателя.

### 0.2. Что входит в план

- `core41`: сведение `resolve_work`, `_receive_work` и `Automaton.receive`
  к одному пути.
- Кампания автоматов: `perform()`, 65 работ, 17 взаимодействий.
- Дневной мир: действия `WorldEngine.execute()`.
- `payload`: расширяемый реестр и передача в обработчик.
- Проекции: активы, потребности, отношения, органы, флаги.
- UI, диалог, лог, превью, снимки и тесты.
- Документальный статус G-18/§3.0.

### 0.3. Что не входит

- Пересмотр канона `SOURCE_OF_TRUTH.md`.
- Полная переделка баланса мира, ИИ, планировщика, геометрии, BDI.
- Замена детерминированных правил LLM или «чёрным ящиком».
- Удаление именованных работ, органов, фракций и контента.
- Одновременная миграция всех слоёв одним изменением.
- Новые типы энергии, «мана», «влияние как второй бюджет» и т.п.

### 0.4. Определение успеха

Успех — не «поля переименованы», а одновременно:

1. любую работу можно описать как `Work` и провести через
   `receive(work, source, world)`;
2. эффект зависит от получателя и контекста, а не только от записи;
3. энергия списывается, приходит с потерями и сходится в отчёте;
4. старые сейвы, UI и детерминизм не ломаются;
5. поведение откалибровано и объяснимо.

## 1. Целевая архитектура

### 1.1. Слои

```text
┌──────────────────────────────────────────────────────────────┐
│ 1. Контент: capability (JSON)                                │
│    id, label, organ, target-selector, cost, cooldown,        │
│    requirements, template{amount, form, payload, duration},  │
│    hints{essence, ai_priority}                               │
└───────────────────────────────┬──────────────────────────────┘
                                │ build_work(context)
┌───────────────────────────────▼──────────────────────────────┐
│ 2. Отправитель: H_i(O_i, S_i, E_i, F_i, context)             │
│    выбирает цель, платит E, формирует payload                │
└───────────────────────────────┬──────────────────────────────┘
                                │ Work{amount, form, payload, duration}
┌───────────────────────────────▼──────────────────────────────┐
│ 3. Получатель: receive(work, source, world)                  │
│    I_j' = merge(I_j, work)                                   │
│    handler = registry[work.form] или default_receive         │
│    H_j(S_j, I_j', E_j, F_j, отношения, геометрия, третьи)    │
└───────────────────────────────┬──────────────────────────────┘
                                │ WorkReport
┌───────────────────────────────▼──────────────────────────────┐
│ 4. Отчёт: accepted, efficiency, stored, loss, entropy,       │
│    effect, essence, trace                                    │
└───────────────────────────────┬──────────────────────────────┘
                                │ projections.apply(report)
┌───────────────────────────────▼──────────────────────────────┐
│ 5. Проекции: активы, потребности, отношения, органы, флаги   │
│    Производные шкалы; не второй мир                          │
└──────────────────────────────────────────────────────────────┘
```

### 1.2. Инварианты целевой модели

1. **Один путь.** `receive(work, source, world)` — единственная точка
   применения работы. Арена, кампания и мир не имеют собственных
   `resolve_work`-веток.
2. **Эффект — в обработчике.** Capability не содержит `effects`/`failure`;
   обработчик возвращает отчёт, а не пишет состояние напрямую.
3. **Одна энергия.** `amount` в `E`; `cost` — расход `E`; активы —
   проекции. Конверсия актива в `E` — явная операция с потерей.
4. **Контекст явен.** Обработчик получает `I_j`, `S_j`, `F_j`, `E_j`,
   отношения, геометрию, историю и третьи автоматы.
5. **Детерминизм.** Стохастика — только в резолвере (`world.rng`), не в
   обработчике; порядок обхода стабилен.
6. **Наблюдаемость.** Каждая работа оставляет `trace`: что отправлено, что
   принято, сколько потеряно, почему.
7. **Совместимость.** Снимки версионированы; старые читаются; UI получает
   фасад, а не ломается.
8. **Авторский контроль.** Capability и правила обработчика — JSON;
   линтер проверяет полноту и запрещает прямой эффект.

### 1.3. Предлагаемые модули

| Модуль | Роль | Статус |
|---|---|---|
| `core41/types.py` | `Work`, `WorkReport` | расширить отчёт |
| `core41/handlers.py` | `force`/`info`/`default` обработчики | новый |
| `core41/model.py` | `Automaton.receive`, `conversion_report` | использовать как основу |
| `campaign/work.py` | `build_work`, `WorkPlan`, адаптер capability → `Work` | новый |
| `campaign/handlers.py` | реестр обработчиков кампании | новый |
| `campaign/projections.py` | применение отчёта к активам/потребностям | новый (выделить из `effects.py`) |
| `campaign/work_trace.py` | след работы, `essence`, объяснение | новый |
| `campaign/effects.py` | legacy-исполнитель на время миграции | сузить, затем удалить |
| `configs/campaigns/base/handlers/*.json` | правила получателя | новый |
| `configs/schemas/work.json` | схема capability/work report | новый |

Имена модулей — предложение, а не обязательство; важно разделение
ответственности, а не конкретные файлы.

## 2. Принципы реализации

1. **Не ломать работающее.** Сначала shadow-режим, потом применение, потом
   удаление legacy.
2. **Одна фаза — один проверяемый результат.** Не смешивать архитектуру и
   баланс в одном изменении.
3. **Сначала арена, потом кампания.** `core41` — наименьший и наиболее
   каноничный слой; на нём проверяется единый путь.
4. **Сначала данные, потом код.** Capability и правила обработчика — JSON;
   Python только интерпретирует.
5. **Сохранять детерминизм.** Любая миграция проверяется на одинаковых
   seed и снимках.
6. **Сохранять объяснимость.** Отчёт и trace важнее «красивого» эффекта.
7. **Не вводить второй источник истины.** Пока идёт миграция, legacy-путь
   может работать, но не должен порождать новые поля эффектов.
8. **Канон выше профильных документов.** Если документ противоречит
   §2.1/§2.2/§5, менять нужно документ, а не канон.

## 3. Фазы

### Фаза 0. Канон, границы и conformance-базис

**Цель:** зафиксировать, что считается нарушением, и получить
автоматическую проверку, не меняя поведение.

**Изменения:**

- Новый документ решения (например, `docs/WORK_MECHANIC_DECISIONS.md`) с
  явным статусом: G-18 и `AUTOMATA_CAMPAIGN.md` §3.0 — исторический
  компромисс, подлежащий приведению к канону; канон не меняется.
- Список conformance-правил:
  - capability не содержит `effects`/`failure`;
  - нет прямых записей состояния из работ;
  - `form` разрешается через реестр обработчиков;
  - работа имеет `amount` и отчёт `stored/loss/entropy`;
  - обработчик не использует `rng` напрямую.
- Заготовка линтера/теста conformance (без включения в рантайм).
- Зафиксировать `WORK_TRACE_VERSION = 1` и `CAPABILITY_SCHEMA_VERSION = 2`
  как план; фактическое введение — в фазах 2–3.

**Тесты:**

- статический тест: в `configs/campaigns/base/*.json` нет новых
  `effects`-полей (для текущих — whitelist миграции);
- статический тест: `campaign/automata.py` не содержит прямых
  `apply_effects` вне разрешённой точки (пока — маркер).

**Критерий готовности:** правила и статус документов зафиксированы; код не
изменён; тесты-маркеры не падают на текущем дереве (или помечены `xfail` с
явной причиной).

**Флаг:** нет. **Риск:** минимальный.

### Фаза 1. Единый путь `receive` в `core41`

**Цель:** убрать обход `Automaton.receive` в арене; сделать `force`/`info`
обычными обработчиками канала.

**Изменения:**

- `core41/handlers.py`: `force_handler`, `info_handler`,
  `default_handler`; регистрация через `Automaton.set_handler` или фабрику.
- `resolve_work()` (строка 310) больше не содержит `if form == "info"` /
  `if form == "force"`; он строит `Work`, вызывает
  `defender.receive(work, source=attacker, world=...)` и переводит отчёт в
  ожидаемый ареной формат.
- `ArenaAgent._receive_work()` (строка 1192) делегирует
  `target.receive(...)`, а не дублирует коэффициенты.
- `payload` передаётся в `Work` и доходит до обработчика; обработчики арены
  либо читают его, либо явно объявляют `payload_ignored`.
- Сохранить текущие коэффициенты как параметры обработчиков, чтобы
  golden-калибровка не изменилась.
- Флаг `CORE41_UNIFIED_RECEIVE` (по умолчанию `legacy` до приёмки).

**Тесты:**

- эквивалентность: на фиксированных seed и снимках отчёт старого и нового
  пути совпадает в пределах `1e-9` (для `force`/`info`);
- `payload` доходит до обработчика и отражается в отчёте;
- детерминизм: два прогона с одним seed дают одинаковый trace;
- существующие `tests/test_core41.py`, `tests/test_payload.py` проходят;
- калибровочные полосы арены не меняются.

**Критерий готовности:** в `core41/arena.py` нет веток по конкретной форме
вне регистрации обработчиков; `resolve_work` и `_receive_work` вызывают
`receive`; golden-тесты зелёные.

**Флаг:** `CORE41_UNIFIED_RECEIVE`. **Откат:** вернуть legacy-ветку, флаг
не удалять до фазы 7.

### Фаза 2. Адаптер `Work` в кампании (shadow)

**Цель:** научить кампанию строить `Work` и вызывать `receive`, но пока не
применять результат — сравнить с legacy.

**Изменения:**

- `campaign/work.py`:
  - `build_work(capability, actor, target, context) -> Work`;
  - `WorkPlan` с `amount/form/payload/duration/target`;
  - `cost` переводится в `amount` (или в явную конверсию, если цена в
    активе);
  - выбор цели — `target_selector` (self/rival/any/organ/character).
- `campaign/handlers.py`: реестр по форме; на первом шаге — обработчики-
  заглушки, возвращающие отчёт без записи.
- `campaign/automata.py::perform()`:
  1. строит `WorkPlan`;
  2. списывает `E`/цену;
  3. вызывает `target.receive(work, source=actor, world=self)`;
  4. в shadow-режиме **не применяет** результат, а сравнивает с legacy;
  5. в legacy-режиме применяет старый путь.
- `campaign/work_trace.py`: `trace` с `capability_id`, `amount`, `form`,
  `efficiency`, `stored`, `loss`, `entropy`, `essence`, `chance`, `roll`.
- Флаги: `CAMPAIGN_WORK_BUILD` (строить), `CAMPAIGN_WORK_APPLY`
  (применять), `CAMPAIGN_WORK_SHADOW` (сравнивать).

**Тесты:**

- shadow-тест: для 65 работ на наборе состояний новый путь строит работу и
  отчёт без исключений;
- расхождение `legacy vs work` логируется, но не меняет состояние;
- детерминизм: одинаковый seed → одинаковый `WorkPlan`;
- ни одна работа не создаёт `Work` с `amount <= 0` без явного
  `free`-флага;
- `campaign/effects.py` не вызывается из нового пути в shadow-режиме.

**Критерий готовности:** 100% работ и 17 взаимодействий проходят
`build_work`; shadow-отчёт стабилен; поведение игры не изменилось.

**Флаг:** три флага выше. **Откат:** выключить `CAMPAIGN_WORK_BUILD`,
оставить legacy.

### Фаза 3. Разделение capability и обработчика

**Цель:** убрать `effects`/`failure` как источник эффекта; перенести
авторский замысел в правила получателя.

**Изменения:**

- Схема capability v2:
  ```json
  {
    "id": "imperial_edict",
    "label": "Опубликовать имперский эдикт",
    "organ": "justice",
    "target": "rival",
    "cost": {"energy": 0.06},
    "cooldown": 1,
    "requirements": {"self": {"legitimacy": {"min": 0.3}}},
    "template": {
      "amount": 0.06,
      "form": "information",
      "payload": [{"kind": "decree", "topic": "legitimacy"}],
      "duration": 1.0
    },
    "hints": {"essence": "legitimize", "ai_priority": 1.4}
  }
  ```
- Правила обработчика — `configs/campaigns/base/handlers/*.json`:
  - выбор ветки по `accepted/success/margin`;
  - входы: `form`, `payload`, `S_j`, `I_j`, отношения, геометрия;
  - выход: `WorkReport` с `effect` и `projections`;
  - общие правила по форме + переопределения по получателю/органу.
- Миграция 65 success + 65 failure веток в правила. Это не механический
  перенос: каждая ветка переписывается как «что получатель делает с
  работой», а не «что автор обещает».
- `essence` становится вычисляемой: `trace.essence = classify(form,
  payload, report)`; `hints.essence` — только UI-подсказка, не влияет на
  эффект.
- `attack_asset`/`defense_asset` удаляются из capability; их роль переходит
  к `inputs`/`resistance` обработчика и `success_probability`.
- `base`/`slope` заменяются именованными коэффициентами успеха.

**Тесты:**

- линтер: capability не содержит `effects`, `failure`, `attack_asset`,
  `defense_asset`;
- покрытие: для каждой формы есть обработчик; для каждой capability —
  правило или явный `default`;
- эквивалентность: на калибровочном наборе состояние после работы
  совпадает с legacy в допустимом допуске (см. §7);
- контекстная чувствительность: одна и та же capability при разных
  состояниях/отношениях получателя даёт разные эффекты (не только шанс);
- `essence` не читается из capability в расчёте (статический тест).

**Критерий готовности:** 65 capability валидны по схеме v2; 130 веток
мигрированы; `effects`/`failure` отсутствуют; поведение в допуске.

**Флаг:** `CAMPAIGN_WORK_APPLY` включается после приёмки. **Откат:**
вернуть legacy-конфиг и выключить флаг.

### Фаза 4. Взаимодействия и дневной мир

**Цель:** убрать отдельные типизированные механики; всё взаимодействие —
работа.

**4a. Взаимодействия кампании.**

- 17 записей (`organ_interactions`, `automaton_interactions`,
  `character_interactions`) переводятся в capability + `Work`.
- Числовые поля (`integrity`, `faction`, `relation`, `needs`,
  `personality`, `morale`, `organ_integrity`, `source_integrity`,
  `target_integrity`) становятся параметрами обработчика, а не готовыми
  эффектами.
- `perform_organ_interaction`, `perform_automaton_interaction`,
  `perform_character_interaction` становятся тонкими фасадами:
  `build_work` → `receive` → `projections.apply`.

**4b. Дневной мир.**

- `WorldEngine.execute()` строит `Work` и вызывает `receive`; `immediate/
  success/failure` заменяются обработчиком мира.
- Мир получает собственный набор обработчиков (узлы, институты, природа),
  но тот же `Work` и тот же отчёт.
- Если миграция мира слишком рискованна, она выделяется в отдельный флаг
  `WORLD_WORK_PIPELINE` и отдельную приёмку; смешивать с 4a нельзя.

**4c. Квинтуплы.**

- `configs/naming/interactions/*.json` используются как схема входа
  обработчика: `recipient_input`, `sender_output`, `handlers`, `states`,
  `surrounding_influence`.
- Составить таблицу соответствия 8 типов нейминга и 9 форм кампании;
  расхождения — явные алиасы или новые обработчики.

**Тесты:**

- все 17 взаимодействий проходят `build_work`/`receive`;
- действия мира проходят тот же путь;
- квинтуплы валидируются и используются хотя бы одним обработчиком;
- старые UI-вызовы `perform_*` работают через фасад.

**Критерий готовности:** нет отдельного словаря эффектов у взаимодействий
и мира; один `Work`; флаги 4a/4b независимы.

### Фаза 5. Проекции и запрет прямых записей

**Цель:** состояние меняется только через отчёт обработчика и проекции.

**Изменения:**

- `campaign/effects.py` сужается до `projections.apply(report)` или
  заменяется `campaign/projections.py`.
- `apply_asset_delta()` (строка 403) вызывается только из проекции, не из
  работы.
- Активы остаются производными (`asset_terms`, `derived_asset`); работа
  влияет на драйверы/контекст, а не на «плоское имя».
- Потребности, черты, убеждения, намерения, органы, флаги — только через
  правила обработчика.
- `_apply_branch()` (строка 2315) удаляется или становится частью
  проекции.

**Тесты:**

- статический тест: `campaign/effects.py`/`projections.py` — единственная
  точка записи; `automata.py`/`world.py` не пишут состояние напрямую;
- runtime-тест: любая работа без `trace` отвергается в strict-режиме;
- инвариант §5.2: изменение состояния без `Work` невозможно;
- производность: удаление драйвера меняет актив, прямое имя актива не
  является первичным.

**Критерий готовности:** прямой записи из работ нет; проекции
протестированы; старые шкалы остаются проекциями.

## 5. Совместимость, флаги и снимки

### 5.1. Флаги

| Флаг | Что делает | Когда включается | Когда удаляется |
|---|---|---|---|
| `CORE41_UNIFIED_RECEIVE` | арена идёт через `receive` | после golden-тестов фазы 1 | фаза 7 |
| `CAMPAIGN_WORK_BUILD` | кампания строит `Work` | фаза 2 | фаза 7 |
| `CAMPAIGN_WORK_SHADOW` | сравнивает legacy/new без записи | фаза 2 | фаза 3 |
| `CAMPAIGN_WORK_APPLY` | применяет отчёт вместо `effects` | после приёмки фазы 3 | фаза 7 |
| `WORLD_WORK_PIPELINE` | мир идёт через `Work` | после 4b | фаза 7 |
| `STRICT_WORK_TRACE` | работа без trace отвергается | фаза 5 | фаза 7 |

Флаги читаются из конфигурации/переменных окружения, имеют значение по
умолчанию `legacy` до приёмки. В production-сборке не должно быть
неявного включения.

### 5.2. Shadow-режим

- Строит `Work`, вызывает `receive`, пишет отчёт в отдельный лог.
- **Не меняет** состояние и не влияет на UI.
- Сравнивает: `legacy_effect` vs `work_effect`, `chance`, `roll`.
- Расхождение выше допуска — блокер приёмки, а не «шум».

### 5.3. Снимки

- `CAPABILITY_SCHEMA_VERSION`: 1 (legacy actions) → 2 (capability).
- `WORK_TRACE_VERSION`: 1.
- Чтение: v1 и v2; запись: v2 после фазы 3.
- Таблица алиасов `old_action_id → capability_id`.
- `action_uses`, `cooldowns`, `once` сохраняются по capability id.
- При откате v2-снимок читается legacy-адаптером (dual-read), но не
  перезаписывается в v1.

### 5.4. Совместимость UI

- `perform(action_id)` остаётся фасадом; внутри — capability id.
- `action_options()` возвращает те же поля для UI плюс `trace_preview`.
- `success_effects`/`failure_effects` в UI заменяются
  `preview.expected/range`, но старый ключ может временно оставаться
  синонимом.
- Диалог и кодекс не ломаются: они получают trace.

## 6. Тест-план

### 6.1. Unit

- `Work`/`WorkReport`: схема, обязательные поля, сериализация.
- `conversion_report`: `stored + loss + entropy == amount`.
- `receive`: выбор обработчика, `default_receive`, неизвестная форма.
- `payload`: известный/неизвестный вид, ошибка схемы, pass-through.
- `success_probability`: коэффициенты, границы, отсутствие скрытых форм.
- Проекции: активы производны, прямой записи нет.

### 6.2. Интеграция

- Арена: один такт `force`/`info` через `receive`; golden-полосы.
- Кампания: `perform` → `Work` → `receive` → отчёт → проекции.
- Взаимодействия: 17 записей через тот же путь.
- Мир: действие → `Work` → `receive` → проекции.
- UI: превью = фактический отчёт в допуске.
- Диалог: `trace.essence`, read-only.
- Снимки: v1 → v2 → roundtrip; старые сейвы.

### 6.3. Property-based

1. **Сохранение:** для любой работы
   `abs(stored + loss + entropy - amount) < eps`.
2. **Нет бесплатных действий:** `E_after <= E_before - cost + eps`;
   исключение — явный `free`-флаг с причиной.
3. **Нет роста из воздуха:** сумма `E` источника и получателя не
   увеличивается больше, чем на `stored` (с учётом внешних источников).
4. **Детерминизм:** одинаковый seed + снимок → одинаковый trace.
5. **Контекст:** изменение состояния/отношений получателя меняет эффект
   (не только шанс) хотя бы в одном сценарии на форму.
6. **Отсутствие прямых записей:** любое изменение состояния имеет trace.
7. **Композиция:** работа организации распределяется между детьми без
   двойного счёта.
8. **Идемпотентность отчёта:** повторное применение того же отчёта не
   удваивает эффект (проекции идемпотентны или явно одноразовы).

### 6.4. Golden/калибровка

- Арена: существующие полосы (смерть/захват/таймаут, медиана тактов) не
  выходят за допуск.
- Кампания: набор seed, до/после; win/loss, длина, использование работ,
  траектории активов.
- Мир: ключевые сценарии (`agora_world.json`) до/после.

### 6.5. Статические проверки

- Линтер capability: запрет `effects`, `failure`, `attack_asset`,
  `defense_asset`; обязательные `template.amount/form`.
- Линтер обработчиков: известные формы, известные проекции, нет
  `rng`/прямых записей.
- Поиск `if form ==` вне реестра обработчиков.
- Поиск `apply_effects`/`apply_asset_delta` вне разрешённых модулей.

### 6.6. Регрессия

- Все существующие тесты, включая `tests/test_automata_campaign.py`,
  `tests/test_payload.py`, `tests/test_core41.py`, UI-тесты.
- Тесты, закрепляющие старую схему, обновляются **в той же фазе**, где
  меняется контракт, а не заранее.

## 10. Открытые вопросы

1. **Тип `Work`.** Использовать `core41.types.Work` напрямую или
   кампанийное расширение? Предпочтение: напрямую, контекст — в
   `payload`/`world`, без второго типа.
2. **Реестр `payload`.** Data-driven JSON-схема или закрытые виды?
   Предпочтение: data-driven реестр + явный pass-through для неизвестных.
3. **Гранулярность обработчиков.** По форме, по фракции, по органу, по
   архетипу получателя? Предпочтение: правило по форме + переопределение
   получателя.
4. **Стоимость в активах.** Как переводить `cost: {influence: 0.06}` в
   `E`? Предпочтение: явная конверсия с потерей; никакого «бесплатного»
   списания актива.
5. **`essence`.** Оставить как `hint` или удалить? Предпочтение:
   вычисляемая + необязательный hint для UI.
6. **Несколько получателей / третьи автоматы.** Одна работа — один
   получатель или веер? Предпочтение: `Work` на одного, веер — несколько
   работ с общей стоимостью.
7. **Допуск калибровки.** ±5 п.п. по win rate и ±10% по длине — принять
   или уточнить после первых прогонов?
8. **Мир.** Мигрировать в том же релизе или отдельным этапом? Предпочтение:
   отдельный флаг/этап, чтобы не смешивать риски.
9. **Удаление флагов.** После одного релиза или двух калибровочных
   прогонов? Предпочтение: два прогона + приёмка.
10. **Документы.** Когда обновлять G-18/§3.0: до или после удаления
    legacy? Предпочтение: после приёмки, но с явной пометкой в новом
    документе уже сейчас.

## 11. Порядок работ и что не делать

### 11.1. Порядок

```text
Фаза 0 ──► Фаза 1 ──► Фаза 2 ──► Фаза 3 ──┬─► Фаза 4a ──┐
                                          ├─► Фаза 4b ──┤
                                          └─► Фаза 5 ───┼─► Фаза 6 ──► Фаза 7
                                                         │
                       (Фаза 6 может идти параллельно 4/5 после 3)
```

- Фазы 0 и 1 можно вести параллельно.
- Фаза 2 зависит от 1.
- Фаза 3 зависит от 2 (shadow).
- Фазы 4a, 4b и 5 независимы после 3.
- Фаза 6 — после 3; UI можно обновлять параллельно 4/5.
- Фаза 7 — последняя, после всех приёмок.

### 11.2. Границы PR

- Один PR — одна фаза/подфаза.
- В архитектурном PR нет изменения баланса.
- В PR миграции контента нет изменения семантики ядра.
- Каждый PR содержит тесты и обновление затронутых тестов.
- Каждый PR оставляет флаги в состоянии «по умолчанию legacy», пока не
  доказана приёмка.

### 11.3. Что не делать

- Не удалять именованные работы: они — capability, а не долг.
- Не вводить типизированную энергию или второй бюджет.
- Не заменять правила LLM/«умным» генератором.
- Не переписывать канон под код.
- Не мигрировать кампанию и мир одним PR.
- Не удалять legacy до калибровки и приёмки.
- Не делать превью эффекта чтением `effects` после фазы 3.
- Не оставлять «временные» прямые записи без trace.
- Не смешивать баланс и архитектуру в одном изменении.

План закрывает GAP-01…GAP-14 в порядке, который сначала доказывает единый
путь на малом слое (`core41`), затем строит кампанийный адаптер в shadow,
затем переносит эффекты в обработчики, унифицирует взаимодействия и мир,
запрещает прямые записи и только после этого переводит UI, сейвы и
калибровку. Именованные работы сохраняются; меняется источник эффекта.
Канон остаётся неизменным, а G-18/§3.0 получают статус исторического
компромисса.
