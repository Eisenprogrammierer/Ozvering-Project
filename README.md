# Инструменты: редактор автоматов, организации и runtime

В ветке `realm/faction-leader` развиваются **контент-инструменты**:
[`automata/`](automata) — графовый редактор конечных автоматов,
[`organizations/`](organizations) — аналитический генератор организаций-
суперсистем с опциональным runtime-слоем для `warfare.py`,
[`naming/`](naming) — конфигурируемый генератор естественных русских названий
и имён, и [`systems/`](systems) — системные автоматы среды, драматурга и
событий. Прежний игровой цикл «Престола» удалён; новый цикл будет другим и
появится позже.

Редактор не навязывает предметную спецификацию (оружие, техника, диалоги и
т.п.): он работает только со **структурой автомата** — состояниями, переходами
и их подписями. Узлы перетаскиваются, переходы создаются в режиме «Связь»,
поддерживаются начальное/финальное состояния, проверка структуры, отмена/повтор
и сохранение в JSON.

```bash
python3 main.py --automata          # редактор автоматов
python3 -m automata                 # альтернативная точка входа
python3 main.py --automata --open example
```

Файлы лежат в [`configs/automata/`](configs/automata); пример —
[`example.json`](configs/automata/example.json). Модель (`automata/model.py`)
не импортирует pygame и не меняет канон `simulation.py`/`warfare.py`.
Подробности — [`docs/AUTOMATA.md`](docs/AUTOMATA.md).

# Аналитические организации-суперсистемы

Пакет [`organizations/`](organizations) выводит автоматы социальных организаций
не из готовых шаблонов, а из **приоритетной потребности** (16 канонических
потребностей `warfare.py`) и **масштаба её удовлетворения** (энергия и
плотность связей). Порог 165 эффективных участников задаёт переход к более
высокому уровню; действует экономика участия — организация живёт, пока есть
желающие, и распадается, когда их не остаётся.

```bash
python3 -m organizations                 # разбор четырёх сценариев
python3 -m organizations --write         # JSON в configs/automata/ для редактора
python3 -m organizations --scenario state_fear --json
python3 -m organizations --runtime --turns 12  # runtime-демо в warfare
```

Примеры: страх + большой масштаб → государство; духовность → церковная
иерархия; статус + малый масштаб → банда; голод/жажда + малый масштаб →
торговая артель. Подробности, формулы и границы — в
[`docs/ORGANIZATIONS.md`](docs/ORGANIZATIONS.md). Слой чистый: без pygame и без
изменения канона `simulation.py`/`warfare.py`.

Runtime-слой подключается к войсковой симуляции опционально:

```python
import warfare as W
from organizations import OrganizationRuntime

det = W.Detachment("линия", "red", [...])
sim = W.WarfareSimulation(seed=7, turns=20)
sim.add_detachment(det)
sim.add_organization(OrganizationRuntime("государство", "red",
                                         detachments=[det]))
sim.run()
print(sim.summary()["organizations"])
```

Организация делает социальный такт после боя: пересчитывает приоритет,
применяет блага/взносы/принуждение к существующим потребностям и морали,
исключает вышедших и распадается без желающих. Без `add_organization`
поведение симуляции не меняется.

# Естественные названия автоматов и имена персонажей

Пакет [`naming/`](naming) строит русские названия автоматов и типов
взаимодействий из декларативных конфигов [`configs/naming/`](configs/naming).
Класс — это функция + потребность + уровень; название собирается по
грамматике `[прилагательные] голова [родительные группы] [фраза]`, а длина
выбирается из усечённого логистического распределения с модой 2 и потолком
10 слов. Морфология согласует род, число, одушевлённость и все шесть падежей.

```bash
python3 -m naming --list
python3 -m naming --mode order --need fear --level 3 --count 5 --seed 7
python3 -m naming --interaction coercion --count 5 --seed 7
python3 -m naming --mode order --ontology
python3 -m naming --person --count 5 --seed 7
python3 -m naming --person --culture russian --gender f --count 3 --seed 7
python3 -m naming --person --fantasy high_elf --count 3 --seed 7
```

`--person` включает отдельный генератор имён: 21 реальная культура и 19
фэнтезийных тем, детерминизм по seed и смешанный режим `generate_many`.
Реальные имена учитывают пол и культурный порядок «фамилия — имя»;
фэнтезийные используют собственные пулы и прозвища. Слой имён не меняет
классы автоматов и типы взаимодействий.

`organizations.generator` использует естественные имена по умолчанию:
seed выводится из разбора, а `build_automaton(analysis, name=..., seed=...)`
позволяет переопределить имя или зафиксировать его. Слой чистый: без pygame и
без изменения схемы редактора. Онтологии классов (входы, выходы, состояния,
вложенные автоматы/схемы, окружение) и пятёрки типов взаимодействий описаны в
[`docs/NAMING.md`](docs/NAMING.md).

# Системные автоматы: среда, драматург и события

Пакет [`systems/`](systems) добавляет два самостоятельных системных автомата
и общий каталог событий:

* **природная среда** — 13 особенностей поля боя (река, овраг, лес, буря,
  руины, пещера и др.) как настоящие автоматы. С ними можно взаимодействовать
  через обычные `Target`/`ActionSpec`/`OutcomeSpec`; исходы возвращают
  эффекты и могут менять состояние особенности;
* **драматург** — эпизодически и стохастически подталкивает акторов к
  поступкам. Оценка соблазна складывается из неопределённости, связности,
  новизны и ставок, а выбор идёт через softmax с температурой, cooldown и
  затуханием новизны;
* **каталог событий** — 88 событий и 176 текстовых шаблонов в 12 категориях
  (жизнь, выборы, война, хозяйство, бедствия, преступления, открытия, тайны,
  любовь, культура, политика, общество). Шаблоны автоматически подставляют
  имена персонажей и организаций.

```bash
python3 -m systems --list
python3 -m systems --environment river --interact ford --seed 7
python3 -m systems --event birth_child --seed 7
python3 -m systems --playwright --turns 20 --seed 7
```

Всё это чистый Python без pygame; канон `simulation.py`/`warfare.py` не
меняется. Конфиги лежат в [`configs/systems/`](configs/systems), имена — в
[`configs/naming/people.json`](configs/naming/people.json). Подробности,
схемы конфигов и API — [`docs/SYSTEMS.md`](docs/SYSTEMS.md).

# Взаимодействия: доменно-нейтральный экран

Пакет [`interaction/`](interaction) — заготовка игрового интерфейса из трёх
панелей: **с кем можно взаимодействовать**, **что с ними можно сделать**
(раскрывается после выбора объекта) и **что может произойти**. Прогноз исходов
намеренно неточен: показывает диапазоны вероятностей, уверенность, скрытые
исходы и долю эффектов, которые вообще не описаны моделью. Это не конкретная
игровая механика, а контракт для будущего контента.

```bash
python3 main.py --interaction      # экран взаимодействий
python3 main.py                    # главное меню -> «Взаимодействие»
```

Модель `interaction/model.py` не импортирует pygame и не меняет канон
`simulation.py`/`warfare.py`; экран `ui/scenes/interaction.py` только рисует и
раздаёт ввод. Выбор объекта → действия → прогноз → фактический исход
детерминирован по seed, поэтому сценарий воспроизводим. Демо-контент
(`interaction/demo.py`) абстрактный. Подробности — [`docs/INTERACTION.md`](docs/INTERACTION.md).

# Что
> **Иерархическая мультиагентная марковская игра с частичной наблюдаемостью, структурированным символьным состоянием и обучением с подкреплением.**

Стратегическая игра, где абсолютно все игровые сущности представлены в виде конечных автоматов. Автоматы основаны на IPO-архитектуре: входы, обработка, выходы, состояние. Персонажи, как частный случай автоматов, дополняются архитектурой BDI. Сущности существуют в среде, представленной как **открытая система-суперсистема** (всеобъемлющий IPO-автомат того же кодекса; §12–14 `docs/MODEL.md`). У каждой сущности две метрики: **сила** (`force`) — накопленный ресурс и целевая функция (максимизация силы), и **энергия** (`energy`) — расходуемый запас, мера способности сообщать работу.

Взаимодействие автоматов сводится к передаче энергии, в процессе которой увеличивается или уменьшается сила. Тип энергии не хранится и не конвертируется — это контекстная фаза автомата: рецептивный тип входа адресата выводится единым законом из его состояния (напор/окно/пул) и скрытой выходной фазы такта, а тип выхода — из выбранного действия адресанта. Вероятность успешной передачи и мощность зависят от входа адресанта, типа энергии и количества работы. Работа - это количество сообщаемой энергии в конкретный момент.

# Математика
Псевдокод (соответствует `simulation.py`; символы — имена кода):
```python
regen      = floor(sqrt(force))          # поток пополнения пула энергии каждый такт
energy     = pool                        # РАСХОДУЕМЫЙ запас; cap: E_MAX_MULT * regen
work       <= min(pool, MAX_WORK, max(MIN_OUTPUT, force // 4))
force      : int (вещественные приросты отдыха/трения накапливаются)
U(action)  = [delta + gamma * (reward(t)) | action]
# delta - затраты на действие, gamma - дисконт (0<gamma<1), reward(t) - изменение силы в момент t

# Восприимчивость входа адресата — триггер Шмитта с гистерезисом
# (масштабный порог, выводится из двух метрик модели — принятой работы w_adopt и силы F):
ON(F)  = max(ON_MIN, ON_FRAC * F)        # накопленное давление >= ON  => вход открыт (окно OPEN_TTL)
OFF(F) = OFF_FRAC * ON(F)                # давление упало ниже OFF     => вход закрыт
# Открытый вход: отдача работы ~ w*m*GAIN_MAX; закрытый: ~ w*m*Y_SMALL (почти нулевая).

# Логистическая прибыль покоя:
rest_gain = MAX_REST_DELTA * (E/L) * (1 - E/L),  L = L_BASE + L_STEP * rest_units
# rest_units растут ТОЛЬКО от реально полученной силы при успешных передачах.
```


# Состояние реализации (актуально)
Рабочая модель — `simulation.py`. Реализовано согласно согласованной архитектуре:
- сущности — IPO-автоматы (+BDI у персонажей), только две метрики: сила (force) и энергия (energy);
- энергия — расходуемый пул, пополняемый в такт ⌊√силы⌋ (regen); работа списывается из пула;
  формула energy = ⌊√force⌋ сохранена как поток восстановления структуры (см. «Математика»);
- тип энергии — контекстная фаза, а не хранимая валюта: не хранится и не конвертируется;
  рецептивный тип входа адресата выводится единым законом из контекста (напор/окно/пул +
  скрытая выходная фаза), тип выхода — из действия адресанта; наблюдатель усредняет по трём
  типам под равномерным (максимально-энтропийным) априором, что возвращает симметрию
  режимов (§2 MODEL.md);
- профиль (`PROFILES`) — один скаляр p ≤ 1, умножающий уже существующие константы;
  канал «ротации защиты» упразднён, автоматического назначения профиля по seed нет (§2а MODEL.md);
- восприимчивость входа адресата — триггер Шмитта с гистерезисом (масштабный порог
  ON(F) = max(ON_MIN, ON_FRAC·F)): упорное давление МОЖЕТ открыть окно, но не гарантирует;
- частичная наблюдаемость — шум наблюдения вместо шума результата;
- отдых — логистическая прибыль с потолком, растущим только от успешной работы;
- агенты: активные сцены используют `core41.ArenaAgent` с `QTablePolicy` и
  `BDIPolicy` (online-обучение); `PolicyAgent` остаётся легаси-мостом, а
  `UtilityAI` — baseline/экспериментом. Условие конца — устойчивое доминирование
  (capture), при этом «жизнь» агенту гарантирована (сила не опускается ниже 1).

# Войсковые автоматы
Слой [`warfare.py`](warfare.py) добавляет новые **виды автоматов**, не меняя канон
`simulation.py` (боевые передачи по-прежнему идут через `run_tick`):

* **персонаж** (`Character`) — IPO + BDI, 16 потребностей (голод, жажда, усталость,
  здоровье, страх, тревога, одиночество, репродукция, знания, творчество, скука,
  статус, духовность, умение, любовь, дружба) и зачин личностных черт
  (`Personality.from_seed`, 12 черт, архетипы);
* **отделение** (`Detachment`) — суперсистема из персонажей; наружу — единая боевая
  единица (одна сила/пул/удар), внутрь — мораль, дисциплина, агрессия и паника;
* **стан** (`Stan`) — суперсистема-источник, выпускающая новые отделения на поле;
* **приказ** (`Order`) — пассивный автомат-транслятор сигнала (агрессия,
  дисциплина, мораль, страх, потребности, запрет отхода) для отделений и персонажей;
* **заградотряд** (`BarrierDetachment`) — отделение, принуждающее своих сражаться,
  а не отступать;
* **подкрепление** (`Reinforcement`) — суперсистема с задержкой ввода отделений.

Демонстрационная двусторонняя симуляция (отделения и персонажи, паники/отходы,
банзай-атаки, работа заградотряда, выход резервов) — `WarfareSimulation` и
`build_demo_scenario` в `warfare.py`; спецификация — [`docs/WARFARE.md`](docs/WARFARE.md).

Кампанийный слой (`view/`) добавляет поверх этого три правила:

* **проекция роты производна, а не закреплена за отделением.** `FrontGeometry`
  каждый такт вычисляет фронт стороны (по движению центра строя или явному
  приказу), а затем относит каждую роту к фронту/флангу/тылу по углу. Развернули
  армию — тот же батальон из тыла становится флангом. Если противник охватил
  строй по всему кругу, проекции считаются радиально: внешнее кольцо — фронт,
  ядро — тыл. Сохраняется только вектор фронта, а не старые метки секторов;
* **логистическая операция действует на несколько рот сразу.** В оверлее
  «Логистика» у каждой роты есть флажок цели, кнопки «Все»/«Никого» и счётчик;
  стоимость умножается на число целей, проверка запасов общая
  (all-or-nothing). Игрок может сознательно не снабжать конкретные роты;
* **здоровье командира — условие поражения.** Когда потребность `health`
  достигает критического значения (`1.0`, в интерфейсе 100), персонаж погибает,
  и сюжет завершает партию по условию `player_dead`. Остальные потребности
  умножают скорость ухудшения здоровья: закрытые замедляют, критические
  ускоряют; смерть необратима. Командир автоматически ест и пьёт из общего
  склада, а личные действия дают сверх нормы, лечение и мораль;
* **черта командира влияет на игру.** «Рыцарь» снижает страх и поднимает
  мораль, «Генерал-учёный» ускоряет конвои и удешевляет операции,
  «Халявщик» увеличивает расход запасов, «Наёмник» даёт влияние, но снижает
  мораль. Эффекты и пересчитанная стоимость действий видны в оверлее
  «Нужды»;
* **конвои идут по маршруту, а не появляются мгновенно.** У них есть ETA,
  риск атаки, полная потеря груза, частичная потеря с задержкой и отдельная
  заявка «Питьевая вода». Бесплатные автоколонны и ночной подвоз тоже
  становятся конвоями; ожидающие грузы и RNG сохраняются;
* **мораль реагирует на стресс.** Она растёт медленно и падает под огнём,
  при голоде, страхе и усталости; плоская прибавка за приказ убрана.
  Порог поражения дивизии — **25 %** потерь, с предупреждениями на подходе
  к нему;
* **прорыв наказывает за удержание потерянного рубежа.** Пока линия цела,
  дивизия несёт умеренные потери. После прорыва `FrontGeometry` оценивает
  локальный контекст каждой роты: враг во фланге/тылу поднимает суточные
  потери до 39–65 %, а полное локальное кольцо — до 104–120 % и через час
  приводит к капитуляции с полными потерями. Организованный отход
  (`withdrawal`) ограничивает их 10 %, но не спасает замкнутое кольцо.
  Канонические `simulation.py`/`warfare.py` при этом не меняются —
  уточняется только контекст кампанийного слоя;
* **армейский автоплан вместо вечного стояния на дистанции огня.** Кнопки
  «Оборона»/«Наступление» (`G`/`T`) задают рубеж или ось наступления для
  всей армии, `Shift+ПКМ` переносит цель, `Y` снимает план. `ArmyPlan`
  распределяет роты по полосам, фиксирует ось (без разворота на 180° при
  проходе армий друг друга) и в соприкосновении продавливает или обходит
  фронт. Ручной приказ временно исключает роту из плана; план и исключения
  сохраняются в снимке кампании.

В игровом UI легаси-стихии `FIRE`/`WATER`/`EARTH` больше не показываются:
на стратегическом поле остался один приказ `ATTACK`, а арена использует
формы работы `force`/`info` из `core41`. Внутренние имена канонического
`simulation.py` не менялись.

Эксперименты — в `experiments/` (запуск из корня репозитория); логи в репозитории не
хранятся — вывод воспроизводится запуском. Текущая воспроизводимая базовая линия

# Графический слой (экраны и наблюдение за партией)

Игровая оболочка — **сценный 2-D слой** [`ui/`](ui): главное меню, настройки,
сохранения/автосохранения, нарративные экраны и игровое поле. Единая точка запуска —
`python3 main.py`. Требуется `pygame-ce` (рекомендуется — корректные шрифты и кириллица):

```bash
pip install pygame-ce
python3 main.py               # игра (старт — главное меню)
python3 main.py --view        # кампанийный интерфейс view (лагерь + RTS-карта)
python3 main.py --fullscreen  # полноэкранный режим
python3 main.py --arena       # арена отдельно (то же, что game_engine.py)
python3 main.py --checkpoint saves/bdi.json   # загрузить BDI-политику в активные сцены
python3 main.py --health-factors aging=1.5,illness=2  # множители здоровья
python3 main.py --sickness 0.5                      # начальная болезнь 0..1
python3 main.py --speed 4                           # 1x/2x/4x/8x/16x
python3 main.py --no-auto-pause                     # без авто-паузы
```

`game_engine.py` — слой «основное игровое поле» (арена + HUD дуэли
`core41.ArenaAgent`: QTable-политика против BDI, одна универсальная энергия,
формы `force`/`info`, ручной режим управления RL-агентом), используемый сценным
слоем как экран `game`; запускается и автономно (`python3 game_engine.py`). Выход
из арены: клавиши `ESC`/`Q` **или клик по кнопке `QUIT` в HUD** (мышью — всегда).

Сценный слой также содержит **пошаговое стратегическое поле (RTS)**: изометрическая сетка
11×9, выбор юнита, приказы движения/давления, контакт, очки команд, высота и
ролевые диалоги командира. Логика — `ui/battlefield.py` (без pygame), экран —
`ui/scenes/battlefield.py`; бой считается `core41.run_duel_tick`, поэтому
легаси-канон `simulation.py` не меняется. Запуск: «Поле боя (RTS)» в меню или
`python3 main.py --scene battlefield`. Ассеты пока — плейсхолдеры
`[ IMG: ... ]` / `[ PORTRAIT: ... ]`.

Целевой 4-2-1-срез и обучаемые агенты вынесены в `core41/` и `agents/`:
`core41` даёт одну универсальную энергию, обработчики, `DuelEnv` и runtime
активной арены (`ArenaAgent`, `ArenaMatch`), а `BDIPolicy`/`QTablePolicy` —
обучаемые политики. Здоровье — отдельное состояние `S` (`H=100`): отдых
`+0.75/тик` восстанавливает его, голод `-1/тик` и переполнение урона с
коэффициентом `0.70` после `F=0` уменьшают; смерть наступает при `H<=0`. Множители
`aging/illness/stress/care` задаются через `--health-factors`. Болезнь —
процесс `sickness ∈ [0,1]`: без отдыха прогрессирует и наносит урон, отдых и
`treat()` снижают её, начальное значение — `--sickness`
(или раздельно `--sickness-rl`/`--sickness-ai`). Лечение — шестое
действие `TREAT` (`CORE_ACTIONS` из шести): политики видят болезнь в
`Observation`, а `TREAT` предлагается только при `sickness > 0`. Успешный
`force`-контакт может передать болезнь асимметрично. `SICKNESS_*`,
`TREAT_ENERGY_FRACTION` и `CONTAGION_*` калибруются через `--set`; `illness`
не удваивает урон от текущей `sickness`. Острая болезнь снижает успех работы
через `work_effectiveness`, не меняя навык и расход `E`. В кампании болезнь,
смерть героя/персонажей и распад организации идут дневным шагом; условия
сохраняются в сейве. Дуэльный
срез откалиброван (`experiments/exp_health_calibration.py`, §2.3.2–2.3.3
`docs/WORLD_CORE_MODEL.md`). Награда арены переопределена: `F`/`H` нормированы,
стоимость `E` — `0.6·ΔE/E_max`, снятие своей болезни `+1.0·Δsickness`, заражение
противника `+0.5·Δsickness`, терминальные победа/поражение `±1.0`
(`reward_delta`/`terminal_reward` в `core41/arena.py`). Обучение —
`python3 -m agents.train --episodes 500 --seed 0` (по умолчанию `ArenaEnv` и
self-play: обе политики обновляются; `--no-self-play` оставляет противника
фиксированным). После обучения CLI играет held-out матрицу силы на отдельных
seed'ах без исследования и обновления весов
(`--eval-episodes`, `--eval-seed`, `--eval-opponents bdi,qtable,random,mlp`;
`--eval-episodes 0` выключает оценку). Ёмкость политик растёт через встроенный
`MLPPolicy` (tanh-MLP с online TD(0), target-сетью с периодической синхронизацией и без внешних зависимостей;
`bdi`/`qtable` — неизменный baseline). Чекпойнты версионированы
(`CHECKPOINT_VERSION = 3`; файлы без поля —
v0): при загрузке QTable мигрирует легаси-ключи 8/10 → 12 полей, BDI и MLP
дополняют веса до 22 признаков; старый MLP-чекпойнт без target-сети копирует
online-веса в target; продолжить обучение можно явно флагами
`--resume`/`--resume-opponent` (для игры есть автопоиск чекпойнта — см. ниже). Дневная кампания подключена к
обучению через `CampaignEnv` (`--env campaign`, проблема №6): одиночный агент,
награда из дельт положения/организации/здоровья/болезни и терминальный бонус
исхода, горизонт дней — усечение; открытые вопросы §7 №28–31 при этом честно
не закрыты. Доменная рандомизация (проблема №7): `--domain-randomize` перед
каждым обучающим эпизодом (arena/campaign) жребует новый домен — профили
(`--profiles CANON,ZEALOT`), стартовую болезнь (`--sickness-min/max`),
health-факторы с джиттером (`--health-factors`, `--health-min/max`) и джиттер
навыков кампании (`--skill-jitter`); draw детерминирован зерном запуска. Held-out
оценка по умолчанию идёт на фиксированном каноническом домене (матрица силы
сравнима между запусками); усреднение по распределению — `--eval-domain-randomize`.
Held-out кампании — одна строка «политика против мира» (`opponent: "world"`),
а усечение горизонта считается ничьей, не поражением.
Время в арене идёт секундным тиком через
`core41.SimulationClock`: скорости `pause/1x/2x/4x/8x/16x`, авто-пауза при
критическом здоровье, критической болезни и завершении партии, ограниченный
догон после сворачивания окна (`--no-auto-pause` отключает автопаузу). `PolicyAgent`
остаётся легаси-мостом для старых тестов и
экспериментов. `agents.load_policy(path)` определяет формат чекпойнта;
`--checkpoint` загружает политику в арену и поле боя. Без явного флага игра
сама находит готовый чекпойнт (`agents/checkpoints.py`: каталог
`checkpoints/`, порядок `best.json` → `latest.json` → свежий `*.json`;
отключение — `--no-auto-checkpoint`, просмотр — `--list-checkpoints`).
Подробности и
ограничения — [`docs/AGENTS.md`](docs/AGENTS.md); активные сцены больше не
импортируют `simulation.py`. Сохранения и настройки —
в `saves/` (в репозиторий не попадают). Подробности сценного слоя —

# Новые слои (MVP, выключены по умолчанию)

Три доработки вкатаны флагами **off**, поэтому канон `run_batch(10)` остаётся
`RL 1 / UtilityAI 9 / no capture 0`:

* **лоссовая агрегация** — `play_game(..., lossy=True)`: суперсистема видит
  агрегат `Observation` (без identity/типа/тайминга), части — только публичное
  окно с задержкой (`observability.py`; снимает двойное нагружение F5);
* **LOD** — `lod.run_duel_lod`: LOD-1 событийный, LOD-2 работа + аналитическая
  интеграция времени, LOD-3 mean-field с областью валидности и fallback
  (`lod.py`; канон `play_game` — LOD-1);
* **энтропия смысла** — `play_game(..., entropy=True)`: `H` по 4 корзинам
  убеждений, `H_cum`-ratchet + lineage, тяжёлохвостый мультипликативный шум
  только на `beliefs`, демпфер опциона `1 - noise_floor` (`information.py`).

Решения, границы MVP и открытые задачи — [`docs/DESIGN_ADVANCED.md`](docs/DESIGN_ADVANCED.md).
